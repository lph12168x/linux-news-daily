OpenAI Codex 协助修复近 20 年老 Radeon R600 UVD 视频 bug，已随 PR 进 Linux 7.5
图形 GPU
面向 Linux 7.5 合并窗口的 AMD 内核图形/计算驱动补丁批次中，藏着一个意外惊喜：修复 R6xx 时代（Radeon HD 2000/3000，近 20 年前）GPU 的统一视频解码（UVD）IP 块 bug。新贡献者 Ted Bullock 排查自己 iMac7,1（RV610/M74，设备 ID 1002:94c8）的视频花屏问题：解码器从系统内存读取压缩视频且 GPU 同时绘制时，视频帧会被破坏；把输入移到 VRAM 后解码正常，禁用 GPU 绘制也不再出错。补丁让这批设备的 UVD 缓冲驻留 VRAM（驱动对部分芯片本已如此），覆盖 RV610、RV620、RV630、RV635、RV670——它们共享 RV6xx 解码路径与 legacy R600 固件。他在 Debian 上完成测试，并明确说明用 Codex 协助调查、测试与写补丁。补丁已被接受，随今日 Alexander Deucher 的 AMD 拉取请求进 Linux 7.5。
同批还包含：JPEG type4 packet 支持、UALink 与 RAS 更新、HDMI 2.x / DSC / VRR / HDR 修复、amdkfd 支持非连续与 CPU-less NUMA 拓扑、drm 层新增从 SCGD 解析 HDMI 2.2 FRL 速率的 EDID 支持等。
关注理由：AI 编码代理下沉到内核图形驱动的 bug 定位与修复，是「老硬件由社区 + AI 维护」的新样本；对团队用 AI 辅助排查驱动级疑难 bug（时序、内存放置类问题）是可参考的实操案例。

Intel Xe 驱动为 Linux 7.5 准备 SR-IOV vGPU profiles 供应（provisioning）
图形 GPU
本周 drm-xe-next 拉取请求包含「Prepare SR-IOV provisioning for vGPU profiles」全部 5/5 补丁：把 PF provisioning-mode 变更与批量优先级供应拆成要求持有 master mutex 的静态 helper，并让 provisioning 模式变更、VF 自动供应与 VF 撤销都在该 mutex 下运行——为即将到来的 vGPU profiles 支持铺路（把单颗物理 Intel GPU 切成多个 vGPU 分给不同 VM），同时消除「模式检查与实际（取消）供应之间模式被并发修改」的竞态窗口。
从时点看，动机与即将到来的 Intel GPU D Series（Crescent Island）对齐——此前已有 D270 vGPU profiles 多 vGPU 的展示。同批还有 CCS iGPU 平台的 suspend 优化、force-probe 加载时不再请求提交 bug report 等改动。
关注理由：SR-IOV / vGPU 是 GPU 虚拟化与算力切分的关键路径，D-Series 数据中心卡上市前先把 provisioning 基础设施做扎实；做 GPU 虚拟化、云原生算力池化的团队值得直接跟进这批补丁的后续演进。

Khronos 成立远程卸载 API 探索论坛：为眼镜 / VR / 无人机等受限设备制定标准化高层卸载
计算 compute
Khronos 宣布成立 Remote Offloading APIs Exploratory Forum（11-12），参与方包括 Ericsson AB、Collabora、Holo-Light 与坦佩雷理工大学，由 Ericsson 与 Collabora 两位联合主席牵头。动机：当下的算力卸载方案把应用锁死在各自的连接层上——开发者为专有框架反复重写应用，还要同时应付多种实时网络协议。拟议中的标准化高层 API 将对应用隐藏连接与传输复杂性，且独立于具体协议、硬件与部署模型，目标场景是智能眼镜、VR 头显、无人机等资源受限设备调用云端与边缘算力。
第一阶段仅收集需求与用例；若反响足够强且 SOW（工作说明）达成，Khronos 会组建工作组制定免版税标准。参与免费开放（非会员亦可加入），讨论受项目 NDA 保护、无 IP 许可义务。
关注理由：「计算卸载走网络」正是远程 GPU/NPU 卸载与高速互联（RDMA 类传输）的标准化延伸；若该方向未来成型为正式标准，将直接影响受限设备远程调用算力的传输层与 API 选型，值得持续跟踪。

Zen 6 SMT 实测：EPYC 9996 2P 开 SMT 约 +29%、9686F 约 +34%，高核数下依然值得开
计算 compute
Phoronix 对已上市的 EPYC 9006「Venice」做 SMT 开关对照测试：96 核高频 9686F 与 256 核 Zen 6C 旗舰 9996 均为双路（分别 192 / 512 物理核），SMT 默认开 vs 禁用，环境 Ubuntu 26.10 + Linux 7.3，近 36 项基准覆盖可扩展至 ~1024 线程的传统可扩展负载。
结论：EPYC 9996 2P 开 SMT 几何平均约 +29% 性能，EPYC 9686F 约 +34%；CPU 功耗仅小幅上升，perf-per-Watt 明显更优。Stockfish、Blender 5.2 等多线程负载收益显著。前提仍是软件自身没有扩展瓶颈——若无，Zen 6（C）上 SMT「依然非常值得」。
关注理由：256 核时代 SMT 的有效性第一次拿到大规模同源数据；对服务器采购默认值、吞吐型（HPC / 推理）负载的容量规划与功耗预算都是直接可用的对照口径。

Polo 1.0 发布：MATE 桌面的新 Wayland 合成器，复刻 Marco 体验并带回桌面立方体
显示 display
偏爱 GNOME 2 血统 MATE 桌面又想进入原生 Wayland 世界的用户有了新选择：Polo 1.0（11-12 发布）。Polo 基于 Wayland 的 Weston 库构建，复用 Marco（GNOME 2 Metacity 的 fork）的窗口管理策略、设置与主题，行为尽量与 X11 下的 MATE 保持一致，并提供 XWayland 支持；还把 GNOME 2 经典效果带了回来——桌面立方体、wobbly windows 等。
项目由 MATE 用户 Kerem Söke 开发，目标是「现代化 MATE 的同时保留 X11 下的行为与手感」；1.0 已在 GitHub 发布，另有 Ubuntu Discourse 介绍帖。
关注理由：继 Hyprland、COSMIC 等之后，传统桌面 Wayland 化再添一例；「Weston 库复用 + 窗口管理策略原样移植」的实现路径，对维护自有显示栈 / 合成器的团队是低成本的参考方案。
