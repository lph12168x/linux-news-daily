Wine 合入 MESA_map_buffer_client_pointer：WoW64 32 位 OpenGL 提速
图形 gpu
CodeWeavers 今年主导的 OpenGL WoW64 改进计划落地：Wine 已合入基于 MESA_map_buffer_client_pointer 扩展的 32 位 OpenGL 缓冲区映射支持（MR !12444），用于改善 64 位系统库运行 32 位 Windows 应用/游戏的场景。此前 Wine 需为缓冲区建立 CPU 侧存储并在 glUnmapBuffer 时拷贝内容，或依赖 Vulkan 资源共享做持久映射；新扩展允许 Wine 直接向驱动提供 32 位地址范围映射缓冲对象，让依赖应用侧缓冲上传管理的遗留应用以高效速度走 legacy 映射路径。该扩展 2 月提出、3 月合入 OpenGL-Registry；驱动侧 Zink 已实现，RadeonSI 的 MR !40750 评审中。Wine 侧支持将随周五发布的 Wine 11.21 亮相。
关注理由：WoW64 是 Wine/Proton 32 位游戏的长期软肋；OpenGL 缓冲映射绕开拷贝是真实性能收益，Steam Play 上大量老 D3D/OpenGL 游戏会受益，值得在 Wine 11.21 发布后实测。

Linux 7.4 为 IO_uring 引入 DMA-BUF 支持：I/O 路径零拷贝时代开启
图形 gpu
Linux 7.4 合入 IO_uring I/O 路径的 DMA-BUF 支持基础设施，由 Meta 的 Pavel Begunkov 主导、历经 11 轮评审。DMA-BUF 是 GPU 驱动间免 CPU 拷贝共享硬件缓冲的框架，此次把它带进通用 I/O 路径：以 opt-in 文件操作实现，用户 API 构建在 IO_uring 注册缓冲区之上（dmabuf 以特殊方式注册后即可像普通注册缓冲一样用于 IORING_OP_READ/WRITE_FIXED 请求），配套请求计数、生命周期管理与失效机制。当前仅支持 NVMe 裸块设备，单块 DMA-BUF 最大 4GB；补丁封面信中的基准数据相当亮眼。
关注理由：DMA-BUF 与 IO_uring 是 Linux 近十年最重要的两条零拷贝基础设施，二者打通意味着 GPU 显存与 NVMe 存储间可绕过 CPU 直接读写——AI 推理权重加载、GPU 直接落盘等场景的空间被打开，后续支持更多设备类型的扩展值得跟踪。

Firefox 159 发布：修复 AMD Linux 图形内存暴涨问题
图形 gpu
Firefox 159 双周更发布。Linux + AMD 图形用户的重要修复：在查看地图/地点结果（如 ChatGPT 网页内嵌地图）时 Firefox 会发生过度内存使用，内存占用飙升的问题已解决。另一项 Linux 相关修复是 Wayland 下标签页被误分离为独立窗口的缺陷（159 Beta 引入）。其他变化包括 AI 集成改进、已保存密码默认进侧栏、Web 开发者侧默认启用 scroll-driven animations 等。
关注理由：Radeon 用户浏览器内存暴涨是近期常见抱怨，该修复直接相关；Wayland 标签页误分离也是 159 Beta 引入的恼人回归，桌面 Linux 用户建议尽快更新。

KDE Plasma 6.8.2 发布：数十项修复继续打磨
显示 display
继两周前的 Plasma 6.8（KDE 30 周年版）与上周的 6.8.1 之后，Plasma 6.8.2 带来又一批数十项修复：KWin 的 Wayland 修复、平铺壁纸代码修复动画图片不再播放的回归、KPipeWire 现在向 libx264 传递流的实际帧率、Plasma Big Screen 行列布局重做、桌面图标消失问题修复、大量 Plasma Workspace 修复，以及 Union 主题引擎更新。
关注理由：6.8 系列处于密集打磨期，6.8.2 已是两周内第二个点版本；KPipeWire 帧率传递对录屏/串流画质有直接影响，Wayland 修复对日常桌面稳定性重要，升级无脑跟。

Beeper：内核 eBPF 做应用层解析，Web 服务器吞吐最高 4.5 倍
计算 compute
来自 ETH Zurich、NYU 与 NVIDIA 研究人员的开源项目 Beeper，把 L7 应用层解析搬进内核 eBPF：用 Rust 在 eBPF 中实现 HTTP 解析器并配备内核态 HTTP 缓存，高负载下 Web 服务器吞吐提升 3 倍（实测最高 3.4 倍）；其衍生的 hyper-fast-path 项目作为 Hyper Rust HTTP 库的 eBPF 快速路径，最大吞吐提升达 4.5 倍。该项目在本月 Linux Plumbers Conference 2026 上发表，代码已在 GitHub 开源，用例包括应用层流量监控、缓存与基于载荷的重定向等。
关注理由：eBPF 的能力边界再次被推到应用层协议解析，这是「内核旁路」之外的另一条加速路线；若后续有生产级实现（尤其配合内核 HTTP 缓存），对高并发 Web 基础设施有实际价值。

树莓派 Zero 3 W 与 Pi 4 Model A 设备树现身内核树：新一代 Zero 临近
计算 compute
官方树莓派 Linux 内核树合入两份新设备树：树莓派 Zero 3 W 与树莓派 4 Model A。Zero 3 W 是时隔五年对 Zero 2 W 的继任（期间用户一直猜测是否会有后继机型），其设备树显示沿用树莓派 4 的 Broadcom BCM2711 SoC（四核 Cortex-A72），其余规格尚未披露；Pi 4 Model A 则是 Model A 系列传统——更小、功耗更低、砍掉以太网与部分 I/O 换取更低价格。在内存与元器件涨价的当下，低成本老平台型号重新出现颇有意味。
关注理由：Zero 3 W 若沿用 BCM2711 则意味着图形（VideoCore VI）与计算能力与 Pi 4 持平但体积/价格更接近 Zero 系列，对嵌入式显示方案与边缘部署是低成本新选项；设备树合入通常是正式发布的前兆。
