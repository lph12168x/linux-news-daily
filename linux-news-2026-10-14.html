NVIDIA Nova 驱动随 Linux 7.4 大幅扩建：GPU 信息 ioctl、VRAM buddy 分配、BAR1 CPU 直访
图形 GPU 内核 kernel
面向 Linux 7.4 合并窗口（预计下周 7.3 正式版发布后打开）的 DRM Rust 变更已提交 DRM-Next，其中主体正是 NVIDIA 的 Nova 驱动——它持续领跑内核态 Rust GPU 驱动开发，并顺带把 Rust DRM 基础设施一步步建起来。
本期 Nova 的重点新增：
① NovaCoreApi——供子驱动使用的核心 API 抽象；
② 新的信息上报 ioctl——向用户态暴露 GPU 架构 / 芯片 ID / vRAM 规格等；
③ VRAM buddy 分配器、TLB 刷新、MMU v2/v3 页表类型等一整套内存管理工作，包括经 BAR1 让 CPU 直接访问已映射的 vRAM；
④ 错误上报改进、新的自测、固件处理更新等底层改动。
同批还有 Arm Mali 实验性 Rust 驱动 Tyr 的若干修复。上周 LPC 2026 上 Nova 的定位仍是「最终取代 Open RM、让官方驱动改用上游 Rust 内核模块」。
关注理由：这是 Nova 从「骨架」走向「可用驱动」的关键一步：buddy 分配器 + MMU 页表 + BAR1 CPU 访问，正是一块 GPU 驱动能真正管理显存的核心拼图——上个月这些还都不存在。
结合 LPC 2026 透露的路线（Turing~Blackwell 已启动 GSP 固件），Rust 在 GPU 子系统的落地速度明显超出预期；对关注开源 NVIDIA 栈（Nova/NVK）的同学，7.4 合并窗口的 Nova patch 系列值得逐个过一遍。

Mesa NPU 栈再进一步：Torx 合入 YOLOX 支持，可用 PyTorch 跑目标检测
计算 compute NPU
Mesa 虽以 GPU 驱动闻名，开发者 Tomeu Vizoso 持续把 NPU 能力推进 Mesa 驱动栈：本次合入了 YOLOX 目标检测模型的支持，落在 Mesa 的 Torx 代码中——Torx 是 Mesa 里面向机器学习模型的编译与执行后端，对接 PyTorch ExecuTorch。
合入后，用户可以用 Mesa 的 NPU 驱动直接跑 YOLOX + PyTorch。
目前的实测平台是 Arm EthosU NPU（NXP i.MX93 SoC）；Etnaviv（Vivante NPU 驱动）据称算子已全部支持，但还缺与 Torx 对接的基础设施工作。
相关代码已进 Mesa 26.3（MR !43945）。
关注理由：Mesa 正在从「图形驱动栈」扩展为「图形 + AI 推理统一驱动栈」：模型走 ExecuTorch 编译、NPU 硬件执行，全程开源上游路径，不依赖厂商私有 SDK。
对做端侧 AI/嵌入式（i.MX93 这类低功耗 SoC）的同学，这是「边缘 NPU 用标准 PyTorch 工具链直接部署」的信号；对 RDMA/加速器方向也有参照意义——统一驱动栈 + 标准编译前端的路线正在 GPU（NVK/Rusticl）与 NPU（Torx/Etnaviv）两侧同时推进。

IREE 3.12 发布：Vulkan 驱动彻底重写，新增实验性 AMD HSA HAL
计算 compute
MLIR 系的端到端编译器与运行时 IREE 3.12 发布，两个大动作：
① Vulkan HAL 由 AMD 工程师 Ben Vanik 彻底重写：面向 Vulkan 1.3，原生队列路径、push descriptors、以及无描述符的 buffer device address 调度 ABI；新 Vulkan 后端让 树莓派 VideoCore VII、Arm Mali 第五代、llvmpipe 也获得支持；
② 新增实验性、可选的 AMD 原生 HSA HAL：直连 HSA/ROCR，走 HSA 队列与 AQL 包，绕开 Vulkan 直接调度 AMD GPU 计算。
另有 CPU 后端执行路径重写，编译器侧加入 NVIDIA Ada/Blackwell 目标与 AMD CDNA5/MI455X、RDNA3 细节。
关注理由：HSA HAL 值得单独注意：AQL 包直投 HSA 队列意味着更低的提交延迟、绕过图形栈的纯计算路径——这正是 ROCm 用户态的核心通道，IREE 把它做成独立可选项，说明ML 编译器栈在 Vulkan 之外重新重视原生 compute API。
重写后的 Vulkan 1.3 HAL（push descriptor + BDA 调度）也大幅降低驱动侧开销；对在 AMD GPU 上部署推理/计算管线的场景，Vulkan 路径与 HSA 路径现在可以在同一框架内 A/B 对比，是很好的评估窗口。

Intel ISPC 1.32 发布：AVX10.2 + APX 支持齐备，还顺带加了 AMD Zen 6
计算 compute
Intel 的 SPMD 编译器 ISPC 1.32 发布（基于 LLVM/Clang，服务 Intel CPU 与 GPU 的单程序多数据编程）：
① 基座升级到 LLVM 23.1.2，从而获得 AVX10.2 与 APX（Advanced Performance Extensions）的完整后端支持——这两项分别瞄准即将到来的 Diamond Rapids 服务器与 Nova Lake 客户端处理器；
② 标准库新增并行位聚集（bit deposit/extract）函数；
③ 有趣的是：--cpu=znver6 已可用于 AMD Zen 6——而且加上这个支持的正是一位 Intel 工程师。
关注理由：AVX10.2 与 APX 是下一代 Intel 服务器/客户端 ISA 的两块新拼图：前者统一 AVX 路线（含 FP4/FP6 等 AI 数据类型支持），后者用 32 个 GPR 与大编码空间改善分支密集代码。编译器栈（ISPC、以及此前 AMD 推进 LLVM 的 ACE 系列）的上游化节奏比硬件上市快得多，意味着新 ISA 的工作负载支持在发布日就会基本就绪。
「Intel 工程师给 ISPC 加 Zen 6」也算一个好玩的注脚：异构生态的交叉支持已成常态，编译器基础设施的竞争早已超越厂商边界。

Firefox 159 Beta：修复 Wayland 下标签页误分离为独立窗口
显示 display
Firefox 159 Beta 发布（正式版两周后），对 Linux/Wayland 用户最重要的修复：Wayland 会话下点击标签页时偶尔把标签拖出、分离成新窗口的问题被修复。
其他变化：保存的密码默认可直接从侧边栏访问（无需手动添加 Passwords 工具）；关闭视频动画效果时，Windows 与 Linux 上菜单/面板淡入异常的修复；以及一批零散修复。
关注理由：这是一个长期困扰 Wayland 用户的交互级 bug——点标签页整页被「甩」出去，虽不至于丢数据，但日常体验极差；该修复说明 Firefox 的 Wayland 原生窗口管理路径（xdg_toplevel 交互）已进入细节打磨期。
对 Wayland 桌面普及来说，这类「最后一公里」的应用层修复比协议特性更有体感，值得在下一个 ESR 汇合时确认是否回移。

内核拟取消 AI/LLM「Assisted-By」标签强制要求，维护者峰会已达成共识
内核 kernel
内核目前的文档要求：补丁若使用了 AI 工具，需以 「Assisted-by:」标签注明。但这一要求即将被取消——Sasha Levin 已在 LKML 发布移除该要求的补丁，上周布拉格维护者峰会已就弃用达成共识，补丁将删除文档中对应的标注要求。
LKML 上意见分裂：一派认为 AI 使用已泛滥、逐条标注没有意义且容易漏标；另一派则希望保留标注的透明度。
背景：这一归因要求今年夏天就已被讨论过一轮（当时已有放弃的苗头）；此前 Linus 本人还公开示范用 Claude Code 开发内核改进，并在补丁说明中坦然承认 LLM 参与。
关注理由：这是内核社区对 AI 补丁洪流的正式制度回应：与其强制标注（无法验证、容易变成形式主义），不如转向依赖既有评审流程兜底——与此前「维护者被 AI 补丁冲击」「网络子系统把 50+ 修复转移到 7.4」的报道是同一条主线。
对内部代码管理有直接参照价值：AI 参与的归因策略正在从「强制标注」走向「评审质量优先」，值得跟踪维持者峰会后续是否出台替代性规范（如抽查、统计口径）。
