GNOME Mutter 改进次级 GPU 拷贝缓冲的 damage 跟踪，多 GPU 体验受益
显示 display
Red Hat 的 Ray Strode 在 Mutter 合入了对次级 GPU 拷贝缓冲（secondary GPU copy buffers）的 damage 跟踪改进（MR !5300），将随 GNOME 51.2 首次出现，也作为 GNOME 52 的早期改进。
背景：当显示器连接在与渲染 GPU 不同的另一块 GPU 上（典型如混合 GPU 笔记本），native backend 需要把渲染好的帧拷贝过去——按拷贝模式不同，使用两个 GPU 可访问缓冲或三个 CPU 可访问缓冲作为目标。
此前的缺陷：主 GPU 拷贝轮换使用三个目标缓冲，复用的缓冲可能是几帧之前的旧内容，只拷贝「最新一帧的 damage」会把旧像素留在屏幕上；序列化次级 GPU 拷贝的两帧假设在拷贝失败后也会与缓冲内容脱节；CPU 回退路径在读取失败后仍返回缓冲。
新方案引入 MetaSecondaryGpuCopyState：记录每个目标缓冲「最后一次成功拷贝的源帧」，保留近期帧的 damage 区域；未知或过旧的缓冲、以及 damage 矩形超过 16 个的区域，直接整帧拷贝；缓冲只有在拷贝成功后才前移，零拷贝导入成功则使回退状态失效。
关注理由：这是多 GPU 桌面显示路径的基础设施级修复：混合 GPU 笔本与多显卡工作站的「外接屏花屏/残影」类问题，大多出在跨 GPU 拷贝的 damage 计算上。
对做显示/合成器方向的同学，这份 MR 是「跨 GPU 拷贝缓冲生命周期 + damage 状态机」的现成参考实现；顺带一提，作者是在做 castkms（虚拟显示 DRM/KMS 实验驱动）与 Pronk（把 Google Cast 设备变成 Linux 桌面显示器）时顺带打磨的。

Intel 确认 Nova Lake S/P 核显支持 SR-IOV，Xe 驱动 VFIO 设备表补上 PCI ID
图形 GPU
Intel 工程师在内核邮件列表贴出补丁，确认 Nova Lake S（NVL-S）与 Nova Lake P（NVL-P）的集成显卡将在 Xe 内核图形驱动下支持 SR-IOV（Single Root I/O Virtualization）；同批补丁也把 Crescent Island（现名 Intel GPU D 系列）的 SR-IOV 支持加进 Xe 的 VFIO 代码。
补丁内容：把 CRI / NVL-S / NVL-P 的 PCI ID 加入 xe-vfio-pci 设备表，让生成的 vfio_pci 模块别名允许用户态为虚拟功能（VF）选择该变体驱动。
时序上：补丁正在评审，而 Linux 7.4 合并窗口下周才开、DRM-Next 截止已过——大概率要等 Linux 7.5 周期，除非作为 7.4 的早期「fix」提前提交。
关注理由：SR-IOV 意味着一块核显可以切成多个虚拟功能分给多台虚拟机——这是 Intel 消费级/商用 SoC 图形虚拟化走向实用的关键一步（此前只有独显/数据中心卡明确支持）。
对云端 Windows/Linux 虚拟桌面、GPU 分享型容器与 VFIO 直通方案，Nova Lake 的核显 SR-IOV 值得提前规划；Xe VFIO 代码路径（xe-vfio-pci 变体驱动）也是研究现代 GPU 半虚拟化栈的好样本。

Steam Linux 客户端终于转正 64 位，并整体迁入 Steam Runtime 容器运行
计算 compute
Valve 发布新版 Steam 客户端 Beta：Linux 版 Steam 客户端主程序正式改为 64 位应用——Linux 玩家社区多年呼吁的「最后一根 i686 独苗」终于移除，用户系统不再需要为 Steam 客户端本身保留 32 位库。
同时，Steam 客户端现在运行在 Steam Runtime 容器内：客户端与游戏共用同一套 Steam Runtime，目标是让客户端在不同发行版上获得一致的运行体验。
这是对今年早些时候 SteamRT 3 Beta（开始为 64 位与容器化做准备）的延续；完整变更列表见 SteamCommunity 公告。
关注理由：Steam 客户端曾是 Linux 桌面强制保留 multilib/32 位库的最大理由；转 64 位后，纯 64 位发行版与最小化容器镜像少了一个主要障碍（Steam 客户端层面——游戏仍可能需要 32 位运行时，但那已被容器封装）。
对发行版维护者是实打实的依赖树减负；对做桌面标准化/镜像裁剪的同学，这也是评估「去 32 位」节奏的参考事件。

Claude Code 实战逆向工程硬件：Red Hat 工程师用它写出扫描仪 SANE 驱动并修好 IPU7 摄像头
内核 kernel
Red Hat 的 Christian Schaller 发博文展示用 Claude Code 逆向工程硬件、为 Linux 补驱动的实践：
① 他的 Pustek 8200i 底片扫描仪在 Linux 上不工作——借助 Claude Code，通过带厂商驱动的 Windows 虚拟机抓取并分析 USB 活动，成功写出可用的 SANE 扫描仪驱动；随后还用 Claude Code 开发了 Rust 编写的 GNOME 底片扫描应用（Negative Vibes）。
② 接着又让 Claude Code 修复 ThinkPad X1 Carbon Gen 14 Aura Edition 上的 MIPI 摄像头问题——该机 Intel IPU7 背后的 Sony 传感器出黑图等故障，AI 同样解决了这些驱动缺陷。
完整过程见其 GNOME 博客。
关注理由：「AI 逆向工程硬件 → Linux 驱动」正在从概念变成可复现的工作流：抓 USB 流量 + 厂商驱动行为 → 生成协议实现，恰好命中驱动开发里最枯燥、最适合自动化的部分。
结合近期内核社区的动态（Linus 用 Claude Code 推进内核分支、Google Sashiko 19 万次评审、AI 辅助逆向），驱动/固件方向的 AI 辅助开发已是明确趋势；对团队而言，「用 AI 补齐冷门硬件支持、减少逆向人力」的工作流值得内部试点。

Ubuntu 26.10 正式发布：Linux 7.3 + GNOME 51 + Mesa 26.2，Rust Coreutils 迁移完成
内核 kernel
Ubuntu 26.10「Stonking Stingray」正式发布（半年期非 LTS 版本），主要更新：
① Linux 7.3 内核（接近最终状态）；
② GNOME 51 桌面及其他桌面选项更新；
③ 图形驱动更新至 Mesa 26.2；
④ Rust Coreutils 迁移全部完成；
⑤ 改进的 TPM 全盘加密与企业认证支持；
⑥ 首次提供 RISC-V 桌面镜像与优化的 amd64v3 安装镜像；
⑦ 新的 Myna 语音转文字技术预览（Canonical 情境感知桌面方向）。
Kubuntu、Xubuntu 等 10 个官派分支同日发布。Phoronix 此前的实测显示 26.10 相对 26.04 LTS 有可观性能提升（新内核 + 组件更新）。
关注理由：作为 27.04 / 28.04 LTS 之前的过渡版，26.10 把 Linux 7.3 + GNOME 51 + Mesa 26.2 这套组合推给了大量桌面用户，也等于把本周刚发布的 Plasma 6.8 / GNOME 51 的图形栈改进（commit-timing、Mutter damage 改进等）送到更广的测试面。
RISC-V 桌面镜像与 amd64v3 ISO 两个「第一次」尤其值得注意——分别对应两条硬件基线演进路线的落地。

Huawei 提议 ACPI CPPC 驱动默认开启 CPU boost 模式
内核 kernel
通用 ACPI CPPC CPUFreq 驱动（大量 ARM64 Linux 服务器平台使用）目前对「最高性能级别高于标称性能级别」的 CPU，boost 模式默认关闭、需要经 sysfs 手动打开。Huawei 工程师的补丁提议默认启用 boost，免去用户态配置。
理由：对服务器平台而言，峰值性能通常是期望的默认行为，现在的默认值并不友好。
ARM 工程师 Christian Loehle 回应提出了更根本的疑问：现代芯片的功耗/热设计包络复杂，boost 开关「既不保证不降频、也不保证拿到请求的性能」，或许应该干脆重新审视 boost 机制本身——懂硅特性的用户可用 scaling_max_freq 自行设上限；并顺带质疑 NOMINAL_PERF != HIGHEST_PERF 平台在 Linux 上是否只是额外的麻烦。
关注理由：表面是一个默认值之争，实质是 ARM64 服务器性能管理接口的清理方向之争：boost 语义在异构/复杂温控时代是否还有存在价值。
对在 ARM64 服务器（含国产平台）上跑计算负载的场景，CPPC boost 默认值直接影响开箱性能基线，这条补丁与后续讨论值得跟踪。
