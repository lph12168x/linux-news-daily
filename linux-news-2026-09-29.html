Mesa 开始开发「Shiva」：为 Vulkan 驱动提供 Gallium3D 式的框架，Faith Ekstrand 在 XDC 2026 提出，先适配 Nouveau 与 Arm Mali Panfrost
图形 GPU
Collabora 的 Faith Ekstrand 在本届 XDC 2026（多伦多）的演讲中提出了一个「给 Vulkan 驱动用的 Gallium3D」设想，并公开了幻灯片。该框架的代号为 Shiva，目前已进入开发阶段。
动机——Vulkan API 变大了，现状不再适用
Ekstrand 坦言：随着 Vulkan API 不断膨胀，现状已经不太好用了。他列举的症状包括：
· Mesa 各家 Vulkan 驱动之间日益碎片化；
· 大量转换层 / helper 堆积；
· 编写一个 Vulkan 硬件驱动的复杂度持续上升。
他在演讲中的原话被引用为：「2016 年实现 Vulkan 又好玩又简单……2026 年的 Vulkan 充满了向后兼容的包袱（cruft）。」更麻烦的是，他预判随着 Vulkan 继续演进，实现难度只会更糟。
Shiva 的定位
· 它是 Mesa 内部一个面向 Vulkan 驱动的框架 / 基础设施，作用类比 Gallium3D 之于 OpenGL 驱动；
· Mesa 的 Vulkan 驱动将面向 Shiva API 而不是直接面向 Vulkan API，由 Shiva 承担各类抽象；
· 设计上前瞻 Rust 驱动等方向。
路线与时间表
· 计划在不久的将来开始动手，初期先适配 Nouveau 与 Arm Mali 的 Panfrost 驱动；
· 预估大约需要两年，才可能真正对用户产出成果。
关注理由：① 「给 Vulkan 做一层 Gallium3D」这件事的分量，要看 Gallium3D 当年解决了什么。Gallium3D 的核心价值不是性能，而是把「驱动共有的部分」从「硬件相关的部分」里切出来：状态管理的簿记、资源对象的生命周期、格式转换、命令缓冲的装配等，所有 GPU 都大同小异；真正需要为每块硬件重写的只有编译与提交那一段。一旦切开，N 个驱动共享一套上游维护的公共层，新增硬件的成本从「写一个驱动」降到「写一个后端」。Vulkan 今天正在经历 OpenGL 当年经历过的同一过程：API 越写越大，每个驱动作者都得把同一套规范语义各自实现一遍，任何规范变更都要乘以驱动数量。Shiva 想做的正是再一次的公共层切分——这是从「为 N 个驱动各写一遍」走向「为 N 个驱动写一次抽象」的必然一步。
② 值得注意的是抽象层被放在了「API 与硬件之间」，而不是「应用与 API 之间」。业界处理 API 复杂度的常见手段是转译层（把新 API 映射到旧 API，如 D3D12→Vulkan、Vulkan→OpenGL），但那类做法要承担完整的语义差异转换，代价高且在语义不对齐处必然出问题。Shiva 是另一种思路：驱动直接面向 Shiva 语义编写，Vulkan 语义的适配在上游只写一遍。这样做的关键前提是Shiva 不是「Vulkan 的子集」而是「Vulkan 能力的规范化表达」——否则驱动会被迫绕过抽象回到原生 API，抽象层立刻退化为可选项。这也是 Ekstrand 必须在社区里先说服各家驱动维护者的原因：这类框架的成败不取决于设计是否优雅，而取决于是否覆盖了所有驱动都真正需要的语义。
③ 为什么先选 Nouveau 和 Panfrost？这个选择透露了真实的驱动力。两家都是社区为主导、没有厂商工程师成建制投入的开源驱动（NVIDIA 与 Arm 的官方投入都集中在各自的闭源或新方案上）。这类驱动人手最少、却要追赶最多的硬件代际，因此对「减少重复代码」的收益最敏感、也最有动力迁移到新框架。这也意味着 Shiva 的落地是「从资源最匮乏处开始」——先在最需要的地方验证抽象是否够用。如果它能在 Nouveau/Panfrost 这种「把每一行代码都当成本」的环境里活下来，迁移到资源充裕的驱动只是时间问题；反之若在这里就被迫频繁绕过抽象，设计一定有缺口。对做平台抽象的人，这是一条很实用的验证顺序：不要先找最配合的伙伴，要找最挑剔、最经不起浪费的那个。
④ 「两年才可能对用户有成果」这个时间表，其实是个相当诚实的工程判断，值得认真对待。框架类工作的特点是前期投入完全不可见：要先定义接口、要先让一个真实驱动跑通、要等上游接受了这套约定，然后才好谈性能。这段时间里旧路径必须继续维护，等于一段时间的「双轨运行」。对使用者与平台的启示是双向的：一方面，看到这个信号后不要指望短期内自己的 Mesa Vulkan 驱动会因此变快或变稳；另一方面，从「两年」这个量级可以反推上游对 Mesa Vulkan 生态碎片化程度的严重性判断——只有共识认为现状真的不可持续，才值得付出两年的双轨成本。任何需要跨多个独立团队协同的架构级重构，都适用这个判断方式：时间表长短本身就是问题严重程度的度量。

NVIDIA 开发 Display Config Server 改善 Linux/Wayland 复杂显示墙：走 Vulkan 直驱显示（VK_KHR_display），「拥有」显示器再租借给客户端，代码将开源
显示 display 图形 GPU
NVIDIA 工程师 Austin Shafer 在 XDC 2026（多伦多）的演讲中介绍了 Linux 在下一代显示墙（display wall）上的方案，并公布了 NVIDIA 正在开发的 Display Config Server。Phoronix 特别指出，这是 NVIDIA 在「AI 之外」改善 Linux 生态的一项努力。
问题场景
· 显示墙指电视制作、影院等场景中的复杂多屏显示系统；
· 目前这类系统大多跑在 Microsoft Windows 上，NVIDIA 希望改善 Linux 在这些视频 / 媒体墙上的使用体验；
· 今天跑 Linux 的显示墙仍然基本是 X.Org Server + NVIDIA Mosaic 显示特性；
· 单靠 Wayland 来做显示墙比较吃力，原因是各家合成器不一、复杂度叠加。
技术出路——Vulkan Direct-to-Display
演讲给出的方向是 Vulkan Direct 2 Display（D2D）：配合 VK_KHR_display 扩展，让 Vulkan 交换链（swapchain）直接驱动物理显示器，完全不需要窗口系统。
Display Config Server 的核心设计——「拥有 + 租借」
· 它由 NVIDIA 自主设计，用来改进 Vulkan 直驱显示模型；
· 做法是让它「拥有」这些显示器，然后租借（lease）给 Vulkan 客户端；
· 这样每个应用就不必各自实现显示器校准与配置逻辑；
· 换来三个好处：集中式配置、客户端之间的无缝交接（handoff）、应用侧更容易实现。
正在进行的工作
· NVIDIA 正在让 Display Config Server 能够与 Wayland 合成器嵌套（nested）运行；
· 同时在改进 Vulkan 直驱显示 API 在显示墙上的呈现能力。
代码计划**开源**，托管于 github.com/NVIDIA/display-config-server，但截至发稿尚未公开可见。
关注理由：① 「拥有显示器再租借」这个模型，解决的是多屏系统里一个被长期低估的问题：配置的组合爆炸。显示墙动辄几十块屏幕，每块都要设定分辨率、刷新率、位置、色彩校准与几何校正。如果每个应用各自去配置，就要面对幂等性、并发、以及「前一个应用改过的状态」这三重麻烦——更糟的是当应用崩溃时，谁负责把显示状态恢复？把「拥有」这一点收归到一个常驻服务后：显示拓扑与校准只被声明一次，应用只表达「我需要一块怎样的显示区域」，交接与回收有了明确的责任方。这与 Wayland 合成器之所以存在是同一个道理（集中管理输出与输入），只是这里的场景连窗口系统都不需要。当系统里有共享的稀缺资源（这里是物理显示器）需要被多个独立客户端交替使用时，「由一个服务居中持有并出租」几乎总是比「各自抢占」更可靠。
② 为什么敢跳过窗口系统直接用 VK_KHR_display？这是对场景的准确判断，而不是技术炫技。VK_KHR_display 允许 Vulkan 交换链绕过合成器直接编程显示控制器，代价是失去窗口系统的诸多保障（多应用共存、合成、输入路由）。对普通桌面这是倒退，但对显示墙恰恰是正确取舍：显示墙上通常只有「一个全屏内容源」在需求上，没有多窗口共存的需要，而延迟、同步精度与逐屏控制的需求却极高。逐屏独立控制尤其重要——多块屏幕拼接时对帧同步（genlock/framelock）和逐屏时序的要求，与「把画面合成到一块虚拟桌面再切分」是根本冲突的。这条经验可以泛化：当一个场景放弃了某个通用机制提供的自由度时，往往是因为它需要更严格的确定性，而不是因为它做不到通用机制能做的事。
③ 「能与 Wayland 合成器嵌套运行」这一点，比看起来更重要，它决定了这套方案是「替代」还是「共存」。如果 D2D 只能独占显示输出，那么使用它的机器就无法同时跑普通桌面——这在制作现场是不可接受的，工程师需要在同一台机器上做配置、监控、日志与资产管理。让 Display Config Server 能嵌套在合成器内部运行，意味着它可以作为合成器的一个客户端存在：由合成器统一持有硬件，再把它要用的那块显示区域租给它，同时保留桌面其他功能。这与 Wayland 生态里一系列「容器化、嵌套化」的做法一脉相承（XWayland、gamescope、各类嵌套合成器）。凡是试图在生产环境替代既有栈的新方案，都必须先回答「如何与既有栈共存」——只做替代、不做共存的设计，几乎不会在真实场景中被采用。
④ 这条消息还给出一个观察 Linux 显示栈走向的信号：Vulkan 直驱正在成为 X11 与 Wayland 之外的「第三条路径」。X11 的问题是架构陈旧（多客户端共享服务端状态、扩展繁多），Wayland 的问题是在特定场景（kiosk、显示墙、VR、机顶盒）里仍然过重。VK_KHR_display 提供了一条极薄的路径：应用直接与显示硬件对话，中间不留常驻服务。对做显示/多媒体平台的团队，值得把这条路径纳入技术选型视野——它不必然是「更好的 Wayland」，而可能是「某些场景下更合适的一类工具」。同时也要清楚它的代价：没有窗口系统，就意味着输入的获取、多进程协调、异常恢复都要自己做或交给上层服务（这正是 Display Config Server 存在的理由）。选型的判断标准应是「这个场景是否真的需要窗口系统提供的抽象」，而不是哪条路径更新。

AMD PerfOpt 随 Linux 7.4 为核显默认开启：GPU 直访系统内存时旁路 IOMMU 地址转换（仅保留权限位校验），减少开销、提升 iGPU 性能，可用 amdgpu.iommu_perfopt 关闭
计算 compute 图形 GPU
使用 AMD 核显（iGPU）的 Linux 用户——特别是性能较强的 Ryzen AI Max+（Strix Halo）与 Gorgon Halo 平台——将随着 Linux 7.4 获得一项新的性能优化。
PerfOpt 是什么
PerfOpt 是 AMD IOMMU Performance Optimization 的缩写，属于 AMD I/O 虚拟化技术（IOMMU）规范的一部分。补丁中的描述为：
· 允许受特权的集成 I/O 设备（即 GPU）在直接访问系统内存时旁路 IOMMU；
· 此时 IOMMU 只强制校验 IR / IW（读 / 写）权限位，不再做 GPA → SPA 地址转换；
· 由驱动显式 opt-in：amdgpu 会在检测到集成 GPU 已处于 identity mode（恒等映射）时开启该特性；
· 若用户希望始终关闭（即便处于 identity mode），可通过模块参数强制关掉。
落地方式与范围
· Linux 7.4 将为 AMD iGPU 默认启用 PerfOpt，预期降低 IOMMU 相关开销、带来可观的性能提升；
· 该特性并非 Ryzen AI Max 专属，对所有 AMD iGPU 普遍有效；但从绝对收益看，Ryzen AI Max 这类平台「可提升的潜力更大」，在今天的 AI / LLM 场景下尤其明显；
· 仅适用于集成 I/O 设备，不适用于独立显卡或其他外部硬件；
· 模块参数为 amdgpu.iommu_perfopt；可在内核 dmesg 中搜索 「PerfOpt」确认是否启用。
来源：AMD 的 Mario Limonciello 提交，补丁经 IOMMU 树并入 Linux 7.4。
关注理由：① 先理解 IOMMU 在这里做什么，才能判断「旁路」是否安全。IOMMU（I/O 内存管理单元）对设备的作用类似 MMU 对 CPU 的作用：设备发出的地址要经过一次重映射才能落到物理内存，从而让设备只能访问被显式授权的区域。这意味着每一次 GPU 访存都要额外走一次地址转换。而「identity mode（恒等映射）」的含义是这张映射表被配置成一一对应——转换的结果与输入相同。既然结果相同，那这次转换在功能上是纯开销，这正是 PerfOpt 得以成立的前提：只在映射已知为恒等的情况下才跳过转换。
② 关键细节是「权限位仍强制校验」——这不是把安全边界拆掉，而是把边界里最贵的那一半优化掉。IOMMU 提供两类保护：地址隔离（防止设备访问不该访问的内存）与权限控制（读写位）。PerfOpt 取消的是地址翻译，保留的是IR/IW 权限检查——也就是说，设备仍无法借旁路去写一块只读区域。这个取舍值得记住：在安全机制的性能优化中，「取消哪一部分」比「取消多少」更重要。保留住那些成本低、但承担了主要风险约束的检查，只在确定无信息量的环节（恒等映射）上省开销，就能拿到大部分性能而不实质降低保护强度。这也是为什么 AMD 要求它由驱动显式 opt-in、且绑定在 identity mode 这一前置条件上，而不是无条件开启。
③ 为什么这项优化对 iGPU 的意义远大于独显？答案是「路径占比」。独立显卡有自己的显存，GPU 绝大部分访存发生在片内显存里，不必穿过 IOMMU；只有跨设备或主机可见的缓冲才走系统内存。而核显根本没有独立显存，与 CPU 共享同一片系统内存，几乎每一次纹理、顶点、帧缓冲访问都要穿越 IOMMU。同一个优化，在独显上是少数路径的加速，在核显上是主路径的加速——这解释了为什么 PerfOpt 明确「仅适用于集成 I/O 设备」，也解释了补丁里要求「集成 GPU 已处于 identity mode」这一条件：核显的固定映射关系使得恒等映射在架构上就是常态。推而广之：评估任何优化时，先算清楚它落在哪条路径上、这条路径在该硬件形态下占总开销的比例，比看优化本身的倍数更有意义。
④ 把这条放在当前 AI / LLM 的背景下看，收益还会被放大。像 Strix Halo 这类统一内存 APU 上跑本地推理时，瓶颈几乎完全落在内存带宽与访存延迟上——模型权重、KV cache 都在系统内存里，GPU（iGPU）与 CPU 反复读写同一块物理内存。在这种「访存即一切」的负载里，任何叠在访存路径上的固定开销都会被直接计入端到端延迟，取消一次地址转换的价值远高于在计算密集型负载中。这条经验对做加速器/统一内存架构的团队尤其适用：当硬件架构走向「CPU 与加速器共享内存」时，连接两者的那条总线与地址转换路径，会从「偶尔穿过」变成「始终穿过」——它的每一纳秒都开始进入关键路径，值得被优先审视。

Firefox 157 发布：Nova UI 号称「多年来最大的一次视觉刷新」，并首次为 WebRTC 视频通话支持硬件 AV1 解码，同时修复 HDR 视频与变速播放的音画同步
显示 display 计算 compute
Mozilla 按双周发布节奏推出了 Firefox 157。
① Nova UI——「多年来最大的一次视觉刷新」
最受关注的变化是新的 Nova 界面，官方称之为「多年来最大的一次视觉刷新」。Nova 的目标是让浏览器外框（browser chrome）、侧边栏与菜单整体现代化。
② WebRTC 首次支持硬件 AV1 解码
· Firefox 157 在支持的设备上为 WebRTC 视频通话启用了硬件 AV1 解码；
· 在此之前，Firefox 对 WebRTC 中的 AV1 视频一直依赖软件解码。
③ 其他改动
· HDR 视频修复；
· 改变视频播放速度时，改善音频与视频的同步；
· 移除内置的 Amazon 搜索引擎。
Firefox 157 的二进制可从 ftp.mozilla.org 下载；Phoronix 也放出了在 Linux 上运行的截图。
关注理由：① WebRTC 从软解切到硬解，改善的不只是性能，而是「持续负载下的功耗与发热」——这对视频通话这种长时段场景才是关键。一次点播视频你可能只看几分钟，但一通会议往往持续半小时以上。软件解码意味着 CPU 全程高占用地执行解码循环，代价直接体现在风扇转速、机身温度与笔记本续航上。硬解把这段工作交给专用解码器，CPU 占用几乎归零。这也解释了为什么浏览器对「通话中硬解」的重视程度一直在提升——它是最容易被用户感知为「笔记本变烫、电量掉得快」的那类负载。评估一项解码能力改进时，除了看它把 CPU 占用降了多少，更要看它作用的负载持续时间有多长——省电类的优化在长时段负载上的价值远高于短时任务。
② 值得想一想的是：为什么 WebRTC 的硬解比点播的硬解难得多，以至于 Firefox 要晚这么久才做到？并非「AV1 硬解很难」，而是两个场景的编码形态根本不同。点播视频通常采用较长的 GOP、较大的参考帧结构、可变码率，允许解码器预读与缓冲；实时通话则要求极低延迟，往往使用专门的低延迟编码配置（如 SVC 分层编码、禁用某些依赖未来帧的参考模式），帧尺寸与结构在会话中还可能动态变化。硬件解码器通常是为「按标准符合性解码一条码流」设计的，而 RTC 场景需要它配合「随时可能切换分辨率、随时可能丢包重同步」的节奏工作，需要额外的驱动与硬件能力支持。这条经验有普遍性：同样一个功能，在「离线/批处理」与「实时/在线」两种场景下的实现难度可能差一个量级——因为实时场景对状态切换与异常路径的要求严苛得多。看到「某能力刚被支持」时，先分辨它之前缺的是算法还是实时性支持，能更准确地判断剩余风险。
③ Nova UI 这类「浏览器外框刷新」，在 Linux 上其实很依赖底层显示栈的成熟度。界面现代化往往意味着更多圆角、半透明、阴影、平滑动画与更细的分数缩放——这些都要求合成器与图形栈提供稳定的帧调度、正确的缩放语义与高效的离屏合成。这也解释了为什么近年来 Firefox 与 Chromium 在 Linux 上的大量工作都压在 Wayland、分数缩放、硬件加速合成这些底层议题上：上层 UI 的表现力，最终受限于下层是否能稳定地按帧交付。对做桌面应用与显示栈的团队，这条链路值得牢记——当界面出现撕裂、模糊、卡顿或缩放不一致时，问题常常不在 UI 代码，而在帧调度与缩放语义的约定上。
④ 最后从生态角度看：开源浏览器在编解码支持上走的是一条「先点播、后实时；先开发版、后稳定版」的渐进路径。回顾火狐近年在视频方面的进展节奏，可以清晰看到这个顺序：先把解码能力接入点播播放，再推进到 RTC；先在 nightly 里验证（比如此前的 Vulkan Video 解码），成熟后再转正到稳定版。这种节奏不是保守，而是因为浏览器是长尾兼容性最苛刻的软件之一：一个解码路径的问题会在千万台真实设备、各种驱动版本上暴露出来，而在开发通道里跑不出这些问题。对采用开源组件的产品团队，这条规律可以直接借鉴：把一个新能力推给全部用户之前，先在可控通道里让它面对最杂乱的环境——真实环境的问题密度，永远高于测试矩阵的想象。

SIMDjson 5.0 发布：静态反射（static reflection）转为正式支持、大整数处理更完善，AVX-512 路线继续把 JSON 解析推向极限
计算 compute
SIMDjson 是开源的高性能 JSON 解析器，多年前率先利用 AVX-512 取得了大幅性能提升，此后持续打磨。如今 SIMDjson 5.0 正式发布。
5.0 的主要变化
· 静态反射（static reflection）支持从实验特性升级为正式特性；
· 大整数（big integer）数字的处理更完善；
· 以及大量较小的特性与性能优化。
性能数据
· GitHub 上的 v5.0.0 发布公告给出了改动说明，以及与 SIMDjson 4.0 的对比基准；
· Phoronix 方面也自行测试了 5.0 对比上一版 4.6.4，在多个吞吐测试（Kostya、FindTweet、LargeRandom、json2msgpack、PartialTweets、DistinctUserID）中 5.0 均为最快，确认在既有优化之上又取得了不错的增益。
更多 CPU 层面的数据可在 OpenBenchmarking.org 的 SIMDjson 测试页查看。
关注理由：① SIMD 解析器之所以能比传统解析快一个量级，关键不在「同时算更多」，而在「先把分支消掉」。传统 JSON 解析器的瓶颈是逐字节判断的分支风暴：每个字符都要问「这是引号吗？是反斜杠吗？是冒号吗？」——分支预测失败会持续打烂流水线。SIMD 路线的做法是先用位运算把整块数据「一次性分类」（例如并行找出所有引号、反斜杠、结构字符的位置），再在这些位置上做逻辑运算定位结构边界，把「逐个字符判断」变成「按掩码批量处理」。这条思路可以套用到任何文本/字节流处理场景（日志过滤、协议解析、正则预筛）：先用 SIMD 把候选位置压出来，再让慢路径只处理少量候选——收益往往来自「慢路径被调用次数减少」，而不是「慢路径本身变快」。
② 静态反射从实验转正，解决的是「解析完了还要手写一堆映射」这个长期痛点。高性能解析器通常只给你「事件流」或「DOM 树」，要用到自己的结构体上，开发者还得写一遍字段名到成员的映射代码——这类代码是纯粹的样板，且随 schema 变化极易不同步。静态反射的含义是在编译期就把结构体的字段信息取出来，由库自动完成「JSON 字段 → 结构体成员」的绑定，运行期几乎零额外开销（因为映射在编译期就固化了）。这与 Rust 生态里 serde 的思路一致：把「粘合代码」从运行期搬到编译期，既消除了手写样板，也消除了运行期查表成本。对做数据密集型服务的团队，这是一个可以直接采用的工程原则——凡是「字段名到成员」这类结构化映射，都优先寻求编译期完成。
③ 大整数处理的完善，暴露了 JSON 作为数据格式一个长期被忽视的边界。JSON 规范里数字只有一种类型，但很多语言的标准 JSON 实现会把它映射到双精度浮点——这意味着超过 2^53 的整数会在解析时静默失真。而现实中的 ID（数据库主键、雪花 ID、区块链哈希片段、大额金额以最小单位表示）大量处于这个区间。这类问题的危险之处在于「不报错」：解析成功、类型正确、只是值悄悄变了，可能到几周后数据对不上才被发现。因此高性能解析器明确支持大整数是正确性的要求，而不是功能锦上添花。这提醒所有做数据交换与接口设计的团队：凡是跨越语言/系统边界传递数值，都要显式确认「超出 2^53 的整数处理策略」，并在接口契约里写清楚——把它留给默认行为，等于把正确性交给实现细节。
④ 从 AVX-512 的持续投入可以看出一个现实：客户端 CPU 裁撤 AVX-512、服务器 CPU 保留，正在把「同一份代码的最优策略」切成两条路。SIMDjson 这类库通常采用运行期指令集分派——在启动时探测 CPU 能力，选择 AVX2 或 AVX-512 的实现路径。这带来一个工程后果：库必须同时维护多套高度优化的内核，且每条路径都要被测试覆盖（否则会出现「功能正确但只在某类 CPU 上慢」的问题）。对使用这类库的产品，有两点实际含义：其一，同一份部署产物在不同代 CPU 上性能可能显著不同，容量规划不能按「最快那台」算；其二，选购或选用硬件时，指令集支持矩阵应被视为真实的性能参数，而不是规格表上的脚注。

Linux 7.4 将引入 Steal Governor：按 vCPU「被偷走的时间」动态收窄首选 CPU 掩码，主动避让超售宿主机上的争抢核心（Kernbench 最高 +14%、Hackbench 最快 +44%）
计算 compute 内核 kernel
已排入今年 10 月的 Linux 7.4 合并窗口的，是一项面向虚拟化世界的 steal governor（被抢占时间调控器）——包含「首选 CPU」驱动与基于 steal 的 vCPU 退避（backoff）机制。
来源与定位
这项工作由 IBM 工程师 Shrikanth Hegde 主导，最初聚焦于提升 POWER 虚拟机性能，后来扩大为通用的 steal governor 驱动与配套基础设施，x86_64 同样受益。它要解决的是今天高核数服务器上「虚拟机超售（over-committed）」时的 CPU 争抢问题。
机制
· steal time（被偷走的时间）指 vCPU 因为宿主机去服务其他虚拟机而等待物理 CPU 资源的那部分时间；
· steal governor 追踪这个值，并据此动态调整「首选 CPU 掩码（preferred CPU mask）」；
· 调度器据此尽量避免把任务放到已超售、或争抢严重的核心上。
设计意图——作者的原话（v14 补丁系列，2026-09-28）
Hegde 写道，该系列是「多轮迭代、重新设计与社区反馈的结果」，「最初是一个架构相关的 RFC，最终演变为『调度器机制 + 虚拟化驱动』的组合」。他明确指出了目标场景：
· 适用于「vCPU 被抢占的代价超过丢失的 CPU 时间本身」的负载，例如锁持有者被抢占（lock-holder preemption）、临界区、以及 TLB / 缓存缺失；
· 数据库负载是典型例子——它混合 OLTP / OLAP 活动，特别容易受这类代价影响，减少 vCPU 抢占有助于提升整体吞吐；
· 但对纯粹的 CPU 时间型负载，可能略有回退。
状态与数据
· 补丁已进入 tip/tip.git 的 sched/core 分支，预计几周后随 Linux 7.4 合并窗口提交；
· 开发者给出的 PowerPC 服务器数据：Kernbench 最高提升 14%、Hackbench 调度基准最快提升 44%、Daytrader 最高达基线的 1.53 倍，而 Phoronix 的 Memcached 基准达到 1.2 倍。
关注理由：① 这条最重要的洞见是一句话：vCPU 被抢占的代价，不等于它被抢走的那点时间。如果一个 vCPU 只是被推迟了几微秒再继续跑，损失就是几微秒；但如果它此刻正持有自旋锁，那么被推迟期间同一锁上的其他 vCPU（可能在其他物理核上）会全部原地空转等待——一次几微秒的抢占，被放大成多个核乘以等待时间的浪费。若它正在临界区中，或者刚因为预热而建立起缓存/TLB 局部性，被挪走还会带来额外的重建成本。这正是「把 vCPU 当作可互换的时间片来调度」这一模型的失效之处：vCPU 之间并非独立，它们通过锁与共享数据结构耦合，抢占一个会连带伤害其他人。理解这一点，就能理解为什么这个问题值得一批专门的补丁来解决——它属于「调度决策的连锁效应」，而不是单机调度里那类「损失一份时间」的问题。
② steal time 被选作反馈信号，是因为它有一个别的指标不具备的性质：它是 guest 唯一能看到的「宿主机层面的真相」。虚拟机内部的任何指标——CPU 使用率、负载、运行队列长度——都只能反映 guest 自己的视角。vCPU 明明「可运行」却没有拿到物理 CPU，这在 guest 内部看起来就是一段凭空消失的时间。steal time 记录的正是这段差距，因此它把宿主机层面的争抢状况暴露给了 guest 侧。不过要注意它的信息性质：这是「症状」而不是「原因」——它告诉你「我在被抢」，但不告诉你「被谁抢、抢得是否有必要」。把它用在「避让」上是合理的（避开已经被证明争抢严重的核心），但用它去推断宿主机负载构成则不可靠。在可观测性设计上这是个通用原则：区分「能反映问题的指标」与「能解释问题的指标」，前者用于触发决策，后者才用于归因。
③ 实现方式选择「收窄首选掩码」而不是「主动迁移」，这个取舍很值得琢磨。面对争抢，一个直觉做法是把被抢的 vCPU 迁到看起来空闲的物理核上。但这会带来两个问题：迁移自身有成本（缓存与 TLB 局部性丢失），而且频繁迁移会让「局部性」永远建立不起来。改为动态调整首选 CPU 掩码、让调度器尽量不从那些核心上挑人，本质上是一种「软亲和」：不去强行动作，而是修改调度的偏好，让不被争抢的核心自然被优先选中。它放弃了「立刻纠正」的激进性，换来更少的迁移与更可预测的行为。这个模式在系统设计里反复出现——当面对争抢与抖动时，与其事后做大幅度纠正，不如事先调整「选择偏好」；前者的收益快但代价持续，后者的收益慢但没有额外成本。当然，软亲和的代价是响应不如强制迁移来得及时，这需要在具体负载下权衡。
④ 「对纯 CPU 时间型负载可能略有回退」这句自我披露，比数据本身更值得重视。它说明这个机制不是无条件的优化，而是一次明确的交换：用「避让带来的额外约束」换取「减少抢占的连锁损失」。对于耦合度低、纯计算型的负载，避让反而可能让任务更难被排到最合适的核心上，造成小幅回退。任何类似的启发式调控都必然带有这种「顾此失彼」的性质，因此工程的正确做法不是想办法让它对所有人都更快，而是：① 保持可关闭（能 opt-out）；② 明确写出适用与不适用的负载特征；③ 让使用者能按负载选择，而不是由内核替所有人决定。对做平台默认值决策的团队，这是可以直接照搬的清单——凡是带有负载偏好的优化，出厂策略就应当包含「如何为不适用场景关掉它」。

NVIDIA Vera SMT 实测：双路 176 个 Olympus 核开启 Spatial Multithreading 后达 352 线程，SMT 相关负载约 +20%，CPU 平均功耗仅增 5%（699W → 739W）
计算 compute 内核 kernel
Phoronix 获得了对一台 NVIDIA Vera 服务器的远程访问权限（含 CPU 功耗与频率监控），并发布了 NVIDIA Vera Spatial Multithreading（SMT）的实测结果。
硬件与平台
· 双路 NVIDIA Vera CPU 超芯片配置：176 个 Olympus 核；
· 开启 NVIDIA 的 Spatial Multithreading 后共 352 个线程；
· 测试环境为 NVIDIA 定制的 Ubuntu 24.04 栈 + Linux 6.17（64K 页）内核 + GCC 15.3；
· SMT 可运行时开关，方式与其他 CPU 相同：/sys/devices/system/cpu/smt/control。
Spatial Multithreading 与 AMD / Intel 的 SMT 有何不同
· Vera 的 SMT 依赖对核心硬件资源的物理分区（physical partitioning）；
· 而 AMD / Intel 的 Simultaneous Multi Threading 走的是对共享执行单元的「动态时间片」；
· 两者都是每核两个线程；
· NVIDIA 认为其 SMT 实现带来更好的资源利用率与更可预测的行为，尤其在 agentic AI 负载上。NVIDIA 官方技术博客将 Olympus 核定位为「为 agentic AI 中的最大单线程性能」而设计。
结论与数据
· 测试选取了大量「能扩展到高核 / 高线程数、且通常在 Intel / AMD 上受益于 SMT」的基准；
· Pogocache 与 Memcached 这类快速缓存软件从 Vera SMT 中受益明显（同时也受益于 Vera 的 LPDDR5X 内存）；
· NVIDIA 此前笼统地描述 Spatial Multithreading 约带来 20% 提升——本次独立、覆盖面广的基准印证了这一说法是准确的（前提是负载本身「SMT 有益且能扩展到高核数」）；
· 频率：无论 SMT 开关，Vera 在全部基准期间最高约 3.2 ~ 3.3GHz，未见明显变化；
· 功耗：双路 Vera 关闭 SMT 平均 699W，开启 SMT（默认）平均 739W，增幅 5%；峰值 1057 ~ 1079W，通常每颗 CPU 在 450W 以内，与 NVIDIA 此前公布的功耗数字一致。
Phoronix 表示后续还会有一系列针对 NVIDIA Vera 不同方向的对比测试。
关注理由：① 「物理分区」与「时间片共享」这两种 SMT 实现的差别，决定了它们在什么场景下值得开——这不是实现细节，而是取舍的核心。传统 SMT 让两个线程共享同一套执行单元，由硬件在每个周期决定取哪条流的指令：如果一个线程正卡在缓存缺失上，另一个正好补位，利用率就上去了；但代价是两条流的执行彼此干扰，单线程的延迟变得不可预测。物理分区则相反：把核心内的资源（如两个 processing element）静态划给两个线程，各自独占，干扰被限制在共享的缓存/内存层级上。结论是清楚的：分区式 SMT 的「单线程延迟」更容易被预测，但资源复用的灵活性更低、对「线程间行为差异大」的负载收益更小；时间片式 SMT 的峰值吞吐潜力更高，但延迟抖动更大。NVIDIA 明确说这套设计面向 agentic AI，正与「分区式」的取舍相匹配——AI 智能体这类负载常常是「长链路、有严格尾延迟要求、线程行为相近」，可预测性比峰值吞吐更值钱。
② 「+20% 性能换 +5% 功耗」是一个划算到不寻常的交换，这背后是一个可以直接用来做容量规划的事实。单纯从能效看，这相当于同样的功耗预算下多出约 15% 的有效算力——在电费与散热构成实质成本的数据中心，这个量级的改善通常要靠一代制程才能换来，而这里只需要打开一个默认开关。更值得注意的是它与频率的关系：SMT 开启前后频率没有任何变化（都在 3.2~3.3GHz）。这一点很重要：它说明收益完全来自「资源的额外利用」而非「把频率推得更高」。如果收益来自提频，那么功耗必然同比例上升、散热设计必须重做、单核延迟也会变差；而收益来自利用率的提升时，硬件的工作点几乎没有改变，因此对热设计与时序裕量的冲击很小。这也解释了功耗只增 5% 的原因——多出的功耗主要来自第二线程带来的额外活动，而非更激进的电压/频率曲线。评估类似「打开某个开关」的优化时，一定要把「性能增益是来自频率还是来自利用率」分清楚，它直接决定了这个增益是否可持续、是否有隐藏代价。
③ 从 176 核开 SMT 到 352 线程，另一个值得记下的判断是「SMT 能否受益，取决于负载能否真正填满两个线程」。Phoronix 明确说明基准的选取标准是「能扩展到高核 / 高线程数、且通常在 Intel / AMD 上受益于 SMT」——这个前提不能省略。历史上 SMT 的收益在两个极端都会消失：线程数不足时（没有第二个线程可调度）、以及内存带宽或缓存已成为瓶颈时（执行单元再空闲也喂不饱）。这次 Pogocache、Memcached 这类缓存软件受益明显，恰好落在 SMT 的甜点区——它们的工作集大量命中缓存、计算与访存交替，执行单元常有空闲周期可以借给第二个线程。因此对实际部署的启示是：SMT 的收益必须按「你自己的负载」实测，不能按「厂商给的平均值」估算；同时要留意那 +5% 的平均功耗是在基准负载下测得的，真实业务负载的功耗曲线可能不同。
④ 最后，这类「第三方独立基准」本身构成了一个值得关注的信号。Phoronix 特别提到能同时监控 CPU 功耗与频率，并说明其数据「与 NVIDIA 此前公布的功耗数字一致」。对硬件厂商而言，功耗与频率的公开数据是最容易被质疑也最难自证的部分——它们高度依赖负载与散热条件，厂商自己的测试环境往往偏向理想。当独立测试能复现同一量级的数字时，这本身提高了后续所有性能宣称的可信度；反之若差异很大，则通常说明测试条件存在未被披露的关键差异。对评估硬件的团队，一个实用的经验是：优先相信那些「同时给出频率、功耗、以及测试条件」的数据，并对只给相对倍率、不给绝对工作点的宣称保持保留态度——因为性能数字脱离了工作点就失去了可迁移性，无法用于你自己的容量规划。
