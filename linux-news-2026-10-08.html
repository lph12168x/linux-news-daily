NVIDIA 615.78.08 Linux 驱动发布：为 VKD3D-Proton 加入 VK_NV_low_latency2 第 3 版，改善 D3D12 游戏的延迟与卡顿（尤其开启帧生成时），并默认让内核接管睡眠时的显存保存
图形 GPU
NVIDIA 于 10 月 7 日发布 615.78.08 Linux 驱动，对通过 VKD3D-Proton 在 Steam Play / Proton 下运行 Direct3D 12 游戏的玩家带来一项实用改进，另含多项修复。
核心改进：VK_NV_low_latency2 第 3 版
· 面向依赖 VKD3D-Proton 的 NVIDIA Linux 玩家，R615 这版驱动加入对 VK_NV_low_latency2 revision 3 Vulkan 扩展的支持；
· 官方说法是改善 VKD3D-Proton 的延迟与卡顿，尤其是在启用「帧生成（Frame Generation）」时；
· VK_NV_low_latency2 的机制是把「渲染队列已排空」的时机提前告知游戏，让游戏据此调度后续的呈现与输入采样，从而缩短从输入到显示的延迟。
其他修复
· 修复游戏 The Last of Us Part II 中观察到的方块状画面损坏；
· 更新内核模块，处理某些 SELinux 配置下的问题；
· 默认启用 NVreg_UseKernelSuspendNotifiers=1——该选项让内核在系统睡眠 / 休眠时自动处理显存保存，不再由驱动自行接管；
· 修复分配大于 2GB 的 GPU 页表时可能失败的问题；
· 修复与 Wayland color-management-v1 协议配合时，Vulkan HDR 内容可能崩溃的问题。
下载与详情见 NVIDIA 官网驱动页。
关注理由：① 先要看清 VK_NV_low_latency2 到底在优化什么，才能判断这个版本号从 2 升到 3 意味着什么。降低输入延迟的经典难点在于：GPU 是深度流水线的，游戏的逻辑帧和 GPU 的渲染帧之间往往隔着好几帧。游戏如果盲目地继续往下渲染，就会在 GPU 队列里堆积大量已经「过时」的帧——玩家的按键其实早就变了，但屏幕上显示的还是几帧之前的画面。VK_NV_low_latency2 提供的是「睡眠 / 唤醒」语义：让 CPU 侧提交下一批工作之前，先等 GPU 队列排空到合适的位置，从而把「排队深度」压下来。版本号从 2 到 3 通常意味着接口在不改变使用方式的前提下扩展了能力或修正了语义，而这次直接受益的是 帧生成——这恰好是延迟问题最棘手的地方。
② 「尤其在开启帧生成时」这句话，点出了这个改进最关键的价值：帧生成天然与低延迟相冲突。帧生成的做法是在两张真实渲染的帧之间，由算法插入一张「生成帧」，因此显示的帧率往往翻倍。但它带来一个副作用：为了给插帧留出空间，管线里会多出额外的缓冲与延迟，玩家可能感觉「帧数很高但手感发飘」。低延迟扩展与帧生成配合时，关键是要让驱动知道「哪些帧是真实的、哪些是生成的」，以便在真实的输入采样点上做同步，而不是被生成帧打乱节奏。这条经验对做实时交互系统的团队普遍适用：当一项「让画面更顺滑」的技术（插帧、平滑、补偿）被引入时，几乎必然要以延迟为代价，二者必须通过显式的同步信号来调和，而不能各自为政。
③ 表面上最不起眼、却可能是最影响日常使用的一项，是默认打开 NVreg_UseKernelSuspendNotifiers=1。它的含义是：系统进入睡眠（S3）或休眠（hibernate）时，显存内容的保存不再由 NVIDIA 驱动独占处理，而是改用内核提供的「挂起通知」机制交给内核统一协调。这个改动之所以重要，是因为睡眠 / 恢复一直是 Linux 上独立显卡最脆弱的一环——显存容量大、保存与恢复耗时长、与系统其余部分的时序必须严格对齐；一旦驱动「自己另外做一套」，就很容易和其他子系统（如内存管理、PCIe 电源管理）的时序打架，表现为恢复后黑屏、花屏或卡死。把它交给内核统一编排，本质上是把「时序正确性」的责任收敛到单一权威处。这是一个很有代表性的取舍：当某个组件自己实现的机制开始与全局机制冲突时，正确的修法往往不是把局部机制改得更聪明，而是让它承认全局机制的存在。
④ 剩下两条修复（>2GB 页表分配、Wayland 色彩管理下的 HDR 崩溃）单独看都很「小众」，合起来却揭示了一类正在变多的风险来源——「放大」。页表大于 2GB，通常出现在大显存、长地址空间或高并发多上下文的场景；而 HDR + color-management-v1 组合，则出现在现代 Wayland 桌面 + 新显示器的路径上。两者的共同点是：功能本身早已存在且「能用」，问题只在规模、组合或新协议接入后才暴露。这给出一条实用的工程判断——当一个系统稳定运行很久之后，新出现的缺陷往往不在「有没有这条功能」，而在「这条功能在更大的规模、更新的组合下是否仍然成立」；因此测试策略的重心应当从「功能覆盖」逐步转向「规模与组合覆盖」。对用户而言，这也解释了为什么「更新驱动」常常能修好一些看似毫不相关的问题：它修的往往不是功能，而是边界。

Valve 的 Timur Kristóf 为十年老卡 AMD Polaris（RX 400/500）实现 RADV 传输队列：修复后 Vulkan CTS 从 50% 失败率变为连续 20 次全过，老显卡上的 Vulkan 可靠性显著提升
图形 GPU
Valve Linux 图形团队的 Timur Kristóf 近年在改善老款 AMD GPU 的 Linux 支持上做了大量工作——包括把 GCN 1.0 / 1.1 时代硬件迁移到现代 AMDGPU 内核驱动。最新的工作是增强 RADV Vulkan 驱动对老款 Radeon RX 400/500「Polaris」显卡的支持。
这次做了什么
· Timur 正在为 Polaris GPU 实现传输队列（transfer queue）支持，用于执行异步数据拷贝；
· 昨日合入的是一批准备性改动与修复，其中最直接的效果是让 Polaris 上的 Vulkan 更可靠；
· Timur 在合并请求（!44800）中原话写道：「有了这些修复，我得以在我们的 CI 那台 Polaris 机器上，用传输队列实现连续完成 20 次完整的 VK CTS 压力测试。（没有这些修复时，它的失败率是 50%。）」
· 也就是说，这些改动让这批十年前的 RX 400/500 级 GPU能够可靠地跑通 Vulkan 一致性测试套件（CTS）。
当前状态与限制
· 代码位于 Mesa 26.3-devel；
· 传输队列支持同时面向 Polaris 与 Hawaii，开发分支为 radv_sdma_legacy；
· 该功能尚未排队进主线 Mesa，且目前需要环境变量 RADV_EXPERIMENTAL=transfer_queue 才能启用。
关注理由：① 「传输队列」这个名词听起来是性能特性，但这次真正的产出其实是「可靠性」——理解这一点的关键，是把它和显卡的引擎分工联系起来。现代 GPU 内部有多个独立的硬件队列：图形队列负责渲染，计算队列负责通用计算，而传输（拷贝）队列专门负责在显存与系统内存之间搬数据。如果只按「一个队列串行做所有事」，那么一次大的纹理上传或缓冲拷贝就会阻塞后面的渲染命令，出现卡顿。支持独立的传输队列后，拷贝可以在后台并行进行。但「支持一条新队列」是一件牵动全局的事：它改变了命令提交、同步栅栏、内存依赖的整套假设，任何一处处理不当都会在压力场景下暴露为不确定性错误——这正是 CTS 失败率高达 50% 的来源。所以这条新闻的实质是：把一条早已存在于别处的并发路径，正确地移植到一个新的硬件代际上。
② 用「50% 失败率 → 连续 20 次全过」来描述进度，是一个非常有信息量的表述方式，值得单独琢磨。它没有给出任何「性能提升 X%」的数字，而是给了一个稳定性指标。原因在于：对于涉及并发与异步拷贝的改动，最有价值的结论不是「跑得更快」，而是「结果是否确定」。一次压力测试通过纯属运气不能说明问题；只有当失败率从「掷硬币」降到「连续 20 次不出错」，才说明底层的时序假设已经自洽。这条经验可以直接搬到任何做并发系统的场景：当你在改造一条异步路径时，衡量标准应当是「重复压力测试下的失败率」而不是「单次运行的耗时」——因为带有竞态的加速是没有意义的加速。
③ 这件事最值得留意的背景，是它的发起方不是硬件厂商，而是 Valve。RX 400/500 是十年前的显卡，对 AMD 而言，为它们持续投入的边际收益已经很低；但对 Valve 而言，这些卡仍然大量存在于 Steam 用户手中，能否在 Linux 上稳定运行直接关系到 SteamOS / Proton 生态的覆盖面。于是出现了一个很典型的分工：由「有商业动机维护存量」的第三方接手本该由原厂承担的维护工作。这条模式对做平台与生态的人有直接启发：当某个组件的原厂退出维护、但用户基数仍然庞大时，机会往往落在「从存量用户中获益的一方」身上——它不需要说服原厂，只需要自己把代码写好并推上游。同时也要看到它的脆弱性：这种维护依赖单一厂商的善意与投入，一旦其战略调整就可能中断，因此在评估可靠性时不能把它等同于原厂支持。
④ 最后，把「尚未进主线、且需要实验性环境变量才能启用」这一点看清楚，能避免不必要的期待。这种状态说明改动仍然被视为实验性：它还没有通过上游维护者关于「长期可维护性」的审视，也还没有被证明在足够多样的硬件与负载上稳定。对使用者的实际含义是：短期内不要指望发行版默认启用它；它的价值目前主要在于「为后续正式合入铺路」，以及为同类老硬件的移植提供可复用的经验。更一般地说，开源硬件支持的推进有一种稳定的次序——先让功能「正确且确定」，再让它「可默认启用」，最后才谈「性能优化」；跳过前两步直接追求第三步，最终都要返工。这条次序与本期第一条 NVIDIA 驱动的思路其实是一样的：先保证边界情形不出错，性能才有意义。

Blender 6.0 可能移除 OpenGL 支持：Blender 5.0 的 Vulkan 后端已趋成熟，官方提案在 6.0（2027 年 11 月）弃用并删除 OpenGL，虚拟纹理是当前主要阻碍
图形 GPU 显示 display
随着 Blender 5.0 的 Vulkan API 支持日趋成熟，Blender 开发者正在考虑在 Blender 6.0 中移除 OpenGL 支持。
当前状态：只是提案，尚未决定
· 官方尚未作出决定，但关于弃用（deprecate）OpenGL 并在 Blender 6.0 移除的讨论正在进行；
· 昨日（10 月 5 日）的 EEVEE 与 Viewport 模块会议纪要确认了这一点，原文写道：「内部提案：在 Blender 6.0（2027 年 11 月）移除 OpenGL 支持。尚未决定，因为虚拟纹理（virtual texturing）会是一个阻碍。」
关键阻碍：虚拟纹理
· 虚拟纹理被认为是移除 OpenGL 的主要阻碍——也就是说，只有当虚拟纹理在 Vulkan 后端上可用，才具备移除 OpenGL 的条件。
时间线与对老平台的影响
· Blender 5.5 是长期支持（LTS）版本，因此它很可能会成为那些仅支持 OpenGL 的老旧平台能够继续使用 Blender 的最后一个版本；
· 文章也指出：到了 2027 年底仍不支持 Vulkan 的系统，本身已经相当老旧，因此这一取舍在时间上是站得住脚的。
关注理由：① OpenGL 与 Vulkan 的差别，本质上是「驱动替你做事」和「你自己安排一切」这两种哲学的差别——理解这点才能明白为什么迁移会拖这么久。OpenGL 是状态机式的接口：应用设置一堆全局状态，然后发出绘制命令，驱动负责编排、校验并在内部做大量翻译工作，灵活但开销隐蔽、并行能力有限，也难以预知性能。Vulkan 则把管理权交还给应用：需要显式地创建管线、管理内存、录制并提交命令缓冲、处理同步与队列——代码量大得多，但行为可预测、可多线程、可对性能负责。对一个已经建立在 OpenGL 假设之上的大型应用（如 Blender 的视口与 EEVEE 渲染器），迁移不是「换个后端」那么简单，而是要把整套资源与状态管理模型重写。所以「Vulkan 后端已趋成熟」这句话的背后，是数年量级的工程投入。
② 「虚拟纹理是阻碍」这个理由非常具体，它揭示了移除一条旧路径的真正条件不是「新路径能用」，而是「新路径能覆盖老路径的全部能力」。虚拟纹理的核心思想是把远超显存容量的巨大纹理当作「虚拟资源」来管理：按需把用到的部分（tile/mip）流式载入显存，用不到的换出，从而让超大贴图或虚拟场景可行。它之所以与图形 API 强相关，是因为它需要精确控制纹理的驻留、页表映射与分页反馈，而这些恰好是低层 API 才能提供的机制。难点在于：在 OpenGL 上，虚拟纹理往往是靠扩展或额外技巧「凑」出来的；迁移到 Vulkan 后，必须用 Vulkan 的方式重新实现同一套语义，并保证渲染结果一致。这带来一条通用的判断规则：要淘汰一条旧技术路径，必须先把「旧路径上那些非主流但真实存在的能力」逐一在新路径上等价实现——否则淘汰只会以极少数用户的功能缺失为代价，而被长期拖延。
③ LTS 版本在这里扮演了一个常被低估的角色：它是「停止支持」这一动作的缓冲垫。把 Blender 5.5 LTS 作为分界点，意味着使用老旧硬件的用户仍能获得一个被长期维护的版本，从而把「技术栈升级」与「被强制断供」两件事解耦：软件可以继续演进，用户也有时间规划升级，而不会在某次更新后突然无法使用。这种「LTS 承接旧平台」的安排，是成熟开源项目处理破坏性变更的标准做法，值得任何在做长期维护的产品借鉴——破坏性变更的正确姿势不是「公告后直接删除」，而是「提供一个被长期支持的旧版本作为落脚点」，把风险从「用户被动承受」变成「用户主动决策」。
④ 从行业视角看，这是整个 Linux 桌面生态「脱 GL 入 VK」大迁移中的一个节点，而它说明这条路线已经走到了应用层。过去几年，合成器、驱动、工具链（如 Zink 把 OpenGL 翻译到 Vulkan）等基础设施层已经大量转向 Vulkan；当像 Blender 这样体量的创作软件开始认真讨论「删除 OpenGL」，意味着迁移已经从「底层就绪」推进到了「上层应用愿意放弃兼容」。这对使用者的现实含义有两面：一方面，新硬件与新特性（更好的多线程、更低的开销）会更快落地；另一方面，「老硬件 + 老驱动」的组合会加速失去支持。从趋势上看，这类迁移最终会形成一条分工清晰的层次——原生 Vulkan 用于新硬件，Zink 之类的翻译层用于过渡期，而陈旧的纯 OpenGL 硬件则被自然淘汰，由 LTS 版本兜底。评估自己是否需要跟进时，真正要问的不是「我的卡支持哪个 API」，而是「我的卡在 2027 年还能拿到被维护的驱动吗」。

Mesa 正筹备正式治理模型：长期依赖非正式共识的做法在开发者倦怠与争议改动上显露短板，拟设立「Mesa 委员会」主要承担冲突解决，新增/移除驱动等争议话题可能交由委员会裁决
图形 GPU
Mesa 3D 驱动栈多年来一直依赖非正式的共识机制运作，而没有正式的治理模型。但在某些场合，这种非正式的处理方式表现并不理想，因此上游 Mesa 开发者如今正考虑建立正式的治理模型。
动机
· 提案明确提及开发者的倦怠（burn-out），以及Mesa 开发者有时没有足够的心力去「顶回」有争议的改动提案；
· 因此正在考虑设立一个委员会（council）来治理 Mesa 开发。
委员会的角色定位
· 该委员会主要聚焦于冲突解决（conflict-resolution），而不是主动驱动决策；
· Mesa 的日常开发实践大体保持不变，仍以共识为基础；
· 只有在无法达成共识、或出现其他议题时，才会求助 Mesa 委员会；
· 可能被提交给委员会裁决的话题包括：新增或移除驱动、遗留软件支持与老驱动移除，以及其他有争议的特性。
进展
· 目前尚无具体提案提交——该话题只是上周在多伦多 XDC 2026 上被提出；
· 相关幻灯片：mesa-governance.pdf。
关注理由：① 先说清楚 Mesa 是什么，才能理解为什么「治理模型」这件事本身值得报道。Mesa 并不是某一家公司的产品，而是Linux / 开源世界几乎所有图形驱动的公共基础设施：Intel、AMD、NVIDIA（NVK/Nouveau）、高通、Arm、Apple（Asahi）等图形栈，以及 OpenGL、Vulkan、OpenCL 等 API 的开源实现，都建立在 Mesa 之上。它的维护者来自数十家公司与独立贡献者，却长期采用「共识 + 无正式章程」的方式运转。这意味着它同时承担了两项矛盾的任务：既要作为一个多方协作的开源项目保持开放性，又要作为事实标准被长期依赖、保持稳定与可预期。当项目规模小、参与者彼此熟悉时，非正式共识是高效的；而当它与整个行业的利益深度绑定后，决策过程本身就成为需要被设计的东西。
② 把委员会的职责限定在「冲突解决而非主动决策」，是一个经过深思熟虑的设计，也是最值得学习的一点。治理机制常见的失败模式有两种：一是完全依赖共识，导致在分歧发生时陷入僵局；二是设立一个权力过大的机构，反而抑制了平时的讨论与自组织。这个提案刻意避开了后者：它把委员会定位为「最后的裁判」而非「日常的管理者」，只有在共识机制失灵时才介入。这样做的好处是保留了共识机制的优点（决策贴合实际、参与者有主人翁感），同时补上了「僵局时如何收场」这一缺口。这条经验可以推广到任何多方协作的组织：一个有效的仲裁机制的标志，不是它平时有多活跃，而是它在「其他机制都失效」时能否给出一个可被各方接受的结论；因此它的触发条件必须明确、且尽量少用。
③ 提案把动机明确归结为「开发者倦怠」与「无力顶回有争议的改动」，这一点比机制设计本身更值得正视。在任何长期开源项目中，有一类成本是隐形的：维护者需要反复亲手去拒绝那些技术上可行、但方向上不合适的提案。单独一次拒绝并不费力，但当它变成高频、且每次都要面对提案者的坚持与社区的争论时，累积的消耗会转化为倦怠——而倦怠的直接后果是维护者离开，这是开源项目最不可逆的损失。把「该不该拒绝」这个判断交给一个有授权的委员会，本质上是在把「政治成本」从个人转移到一个制度化的角色上。对任何依赖关键维护者的组织，这是一条很实用的洞察：当某个关键角色同时承担技术判断与人际对抗两件事时，最该做的不是劝他「更坚强」，而是为「对抗」这件事建立一个不需由某个人独自承担的出口。
④ 提案中列举的那些「可能要交给委员会的话题」，恰好勾勒出开源图形栈当前真正的痛点所在。注意这些话题的共同点：「新增或移除驱动」「老驱动与遗留软件支持的取舍」——它们不是关于「怎么写代码」，而是关于「支持谁、放弃谁」。这类问题的特点是技术上并不复杂（往往写代码不是问题），但牵涉到用户、厂商与维护者之间无法两全的利益——保留老驱动意味着长期维护负担，移除则意味着部分用户失去支持。随着硬件代际快速迭代，这类「资源有限、必须取舍」的决策只会越来越多。由此可以预判一个趋势：未来开源基础设施的治理重点，会越来越多地落在「有限维护资源如何在用户群体间分配」上，而不是纯粹的技术路线之争；衡量一个治理模型是否成熟，也应当看它能否就「放弃」给出被接受的答案，而不只是推动「新增」。

关注理由：① 「借助 AI 又找出 12 个」这句看似轻描淡写的表述，其实指向软件维护中一个正在成形的转变。传统上，这类老代码的漏洞发现高度依赖人力审计或针对性模糊测试，而人力审计的成本随代码规模与历史增长而快速上升，因此像 X.Org Server 这样庞大、历史悠久、边界情形极多的代码库，长期存在大量「已知有风险但没有被具体找出」的位置。当 AI 能以较低边际成本去系统性地扫描这些位置时，结果往往不是「几个新发现」，而是「一批同时被发现」——这正是本期一次披露 12 个 CVE 的结构性原因。由此可以推断一个对运维与安全团队有直接影响的趋势：成熟老代码库的「漏洞披露密度」在短期内会明显上升，但这并不必然意味着软件变差了，而可能只是「发现能力」变强了；相应地，对「老旧但仍在用的基础设施」进行常规补丁跟踪的重要性，会比过去更高，而不是更低。
② 把这些漏洞的组件归类看，会发现它们高度集中在「输入」与「扩展」这两类代码上，这不是巧合。清单里的 XKB（键盘映射）、XInput / XInput2（输入设备与抓取）、XFixes（指针屏障）、Present（呈现同步）、RandR（分辨率与显示提供者）、Glamor（把绘图加速到 GPU）、GLX（OpenGL 胶水层）——它们的共同点是：都接收来自客户端的、结构复杂且长度可变的请求，并且需要解析、分配、再回传给客户端。凡是「解析外部提供的复杂结构 + 手动管理内存」的地方，都是释放后使用与越界问题的天然温床，因为在出错路径上极易漏掉清理或漏掉边界检查。这条规律对任何写解析器的团队都是通用警告：接收变长结构并据此分配内存的代码，必须把「错误路径上的资源回收」与「长度字段的可信性」当作一等公民来审查，而不是依赖正常路径的正确性。
③ 值得注意的是，这些漏洞同时影响 X.Org Server 与 XWayland——这恰好说明「老协议的代码」会以何种方式长期存活在「新架构」里。在 Wayland 桌面中，原生客户端走 Wayland 协议，但大量尚未迁移的 X11 应用仍通过 XWayland 这个「兼容层」运行，而 XWayland 复用的正是 X.Org Server 的同一套协议实现与代码。结果就是：即使你的桌面已经完全转向 Wayland，X11 的解析代码仍然在处理不可信输入，攻击面并没有因为「改用 Wayland」而消失。这对架构演进是一个重要提醒：「替换掉入口」不等于「消除了旧代码的风险」——只要兼容层还在运行，旧实现的每一个解析缺陷都仍然可被触达。因此在做「新协议替换旧协议」的迁移时，安全评估必须把兼容层纳入范围，并把它视为「仍在生产运行的老系统」，而不是「过渡期的临时产物」。
④ 最后，从 2013 年那句「X.Org 的安全性比表面看起来还要糟糕」到今天的 12 个新 CVE，这条时间线本身就值得思考。十多年过去，同样的缺陷类型（释放后使用、缓冲区溢出、越界读写）仍在这一代码库中持续出现，说明这类问题不是「一次修好就结束」的，而是与代码的存续时间同长——只要老代码还在被维护和扩展，新的缺陷就会随新特性一同被引入。更现实的一层是：X.Org Server 的 X11 协议本身早已进入「维护为主、极少新增」的阶段，却依然在持续产出安全修复，这意味着使用者不能指望「它很久没大更新所以应该没问题」。对运维而言，可直接落地的结论有两条：一是把 xorg-server 与 xwayland 的版本更新视为安全更新的常规项（文中已给出 21.1.25 / 24.1.14 这一修复分界）；二是对于暴露在多用户或远程场景下的系统，应默认 X11 会话的协议解析是不可信输入面，优先考虑用 Wayland 原生会话或访问控制来缩小暴露范围。

② 与「新 panel 支持」并排出现的「补上 Gorgon Halo NPU 的一个设备 ID」，构成了一组很有对照意义的例子：同一次 PR 里，一边是数百行的时序与设备树工作，另一边只需要一行设备 ID。这种反差恰恰反映了内核支持工作的真实分布：有些硬件之所以「没被支持」，是因为不了解它；而另一些之所以「没被支持」，纯粹是因为「没人注意到它存在」。文中用「似乎是此前被遗漏了」来描述 Gorgon Halo 的 NPU，正是后者——硬件本身在架构上早就兼容（只差一个 ID），但缺少一次正式的登记，于是用户无法使用。这条经验对做驱动与平台适配的人很实用：在排查「某硬件为何用不了」时，应当先区分「能力缺失」与「登记缺失」——后者往往只需极小改动即可解决，却常常因为被误判为前者而长期搁置。
③ 这批改动出现在「合并窗口前的最后一批 DRM-Misc」，时机本身也说明了内核发布流程的一个运作特征。Linux 的每个版本周期里，新功能必须在合并窗口开启前进入相应的子系统树（这里是 DRM-Next），否则就要等下个周期。因此窗口前的最后阶段，出现的内容往往是「小而确定」的改动——面板设备树、设备 ID、SoC 支持这类风险可控、容易验证的项目，而不是大的架构变更。对使用者的启示是：如果你想判断某个硬件支持「什么时候能到」，最有价值的信号不是厂商公告，而是「它有没有赶上某个合并窗口」；而一旦错过，成本就是以「一个内核周期（约两到三个月）」为单位的等待。这也解释了为什么社区对「截止日期」格外在意。
④ 把这两项放在一起看，能读出一条关于 Linux 硬件支持广度的结论。同一次提交里同时容纳了面向爱好者创客的显示配件（树莓派触摸屏）与面向高端 AI PC 的 XPU（Gorgon Halo NPU），覆盖了从几十美元配件到高端 SoC 的极大跨度。这种「广度」不是偶然：它来自一个由厂商、社区与爱好者共同参与的分布式流程——任何人都可以提交支持代码，只要它能通过评审。这与闭源平台形成鲜明对比：在那里，「要不要支持某硬件」是一个商业决策；而在主线内核里，它更多是一个「有没有人把代码写好」的问题。对普通用户的现实含义是：当你在 Linux 上发现某硬件不被支持时，它更可能是「尚未有人做」而非「被决定不做」——这条判断既解释了为何一些小众硬件反而支持良好，也说明了为何推动上游支持的可行路径是「提交代码 / 提供硬件」，而不是「等待厂商发善心」。

关注理由：① 「为了一个 SoC 新增一个架构符号（ARCH_GOOGLE）」这件事，比它字面上看起来更有分量，因为它牵涉到内核如何组织「设备家族」这一基础问题。内核里的 ARCH_* 符号，本质上是在回答「这块芯片和谁共享代码」：如果两个 SoC 的启动流程、时钟、电源、引脚控制等基础实现高度相似，就可以归入同一个架构目录、共享大量代码。Google 早期的 Tensor（GS101）此前被归到三星架构下，正是因为它是三星 SoC 的衍生物、共享同一套基础。而 G5「走了自己的路」，意味着它在这些最底层的部分已经不再兼容——这时候「归类」就不再是组织上的偏好，而是技术上的必然：强行复用只会带来维护负担与隐患。由此可以得到一条对平台架构的判断规则：「归类」的依据应当是「共享多少底层实现」，而不是「属于哪个品牌或产品线」；当底层实现出现分化时，及时拆分出独立的架构符号，是避免长期技术债的主动选择。
② G1 到 G5 的这条演进线，其实是自研芯片的一条典型路径，值得把它和软件侧的后果连起来看。从「基于成熟 SoC 改」到「完全自研」，中间要跨越CPU/GPU 组合、内存子系统、外设接口乃至电源管理等整条链路。对软件而言，这种转变的现实代价是：此前可以「继承」的底层代码，现在必须重新编写与验证——而这恰恰是「主线支持」需要数年、且必须从头做设备树的原因。文章强调「早在去年就有补丁」，正说明这条路径的周期之长。它的启发在于：硬件自研带来的自由度，最终都会以「软件适配成本」的形式付账；因此在评估自研收益时，必须把「从零建立上游支持所需的年数」计入成本，而不是只看硬件本身的性能提升。
③ 在具体规格里，GPU 的归属是本条最值得图形从业者注意的地方：G5 用的是 Imagination PowerVR DXT-48-1536，而非主流开源栈中常见的 Arm Mali 或高通的 Adreno。这带来一个实际后果：其开源驱动依赖 Imagination 提供的内核驱动（DRM）与 Mesa 中的 PowerVR 后端（PVR），而这条路径历来在开源生态中相对薄弱、推进较慢。相比之下，Arm Mali 有 Panfrost/PanVK 这样的成熟开源实现，高通 Adreno 有 Freedreno/Turnip，NVIDIA 有 Nouveau/NVK——这些都有着活跃的社区与厂商投入。因此这条新闻对 Linux 图形生态的含义是双向的：一方面，Google 设备进入主线意味着 Pixel 上跑 Linux 的可能性更进一步；另一方面，「能启动」与「图形可用」之间仍隔着 Imagination 开源栈的成熟度这道坎。这条区分对任何评估「某设备能否良好运行 Linux」的人都适用：SoC 主线化解决的是「能不能开机」，而「用得爽不爽」取决于 GPU、摄像头、调制解调器等各子系统的开源驱动是否同时到位——两者进度往往相差很远，不能混为一谈。
④ 最后，从更宏观的角度看，这条新闻是「手机 SoC 进入 Linux 主线」这一趋势的延续，而它反映的是 Linux 生态在移动端定位的变化。过去，手机 SoC 的 Linux 支持几乎完全由厂商在 Android 分支中维护，主线内核基本不关心；近年来，无论是通过 SoC 厂商的推动、还是社区的逆向工程，越来越多的移动平台开始向主线靠拢。这一变化的直接受益者不局限于「想在手机上装 Linux」的极客——它还包括单板机、开发板、汽车与各类嵌入式产品，因为这些场景会更廉价地获得某个 SoC 的长期内核支持。对使用者的实用建议是：当你考虑采用某款移动/嵌入式 SoC 做长期项目时，最有价值的尽调指标之一就是「它的支持是否已经（或正在）进入主线内核」——如果是，你能获得持续多年的免费安全更新与硬件适配；如果只停留在厂商 BSP 分支，那么可维护性将完全取决于厂商的持续投入。

③ 「ROCprofiler 引入内核回放（kernel replay）」是一个容易被低估、但对性能工程很关键的能力，值得说清它的意义。GPU 性能分析的一个核心难题是：要评判某个内核（kernel）的快慢，需要把它从整个应用里「单独拎出来」反复测量，才能得到稳定、可比的数据。但在真实应用中，内核的执行与数据、通信、依赖交错在一起，很难在不动整体行为的前提下单独重跑它。内核回放的价值正在于此：它把「现场」保存下来，允许在可控条件下重放同一段工作负载，从而把「测量」与「运行」解耦。这与 CPU 侧的「指令级采样 / 重放」思路同源。对做性能优化的人，判断一个平台是否成熟，可以看它有没有这类「可重复实验」的能力——因为没有被精确定位到具体内核的优化，往往只是在凭感觉调参。它目前处于 Beta，也说明这正是 AMD 在补齐与竞品在工具链成熟度上的差距。
④ 把「升级到 LLVM 24 编译器栈」与「更快的重新构建」放在一起，能看出 ROCm 正在解决一类更根本的问题：开发者体验。GPU 编程工具链的一大痛点是编译慢——大量内核要针对特定架构编译，一次全量构建可能耗时很久，这直接拖慢迭代。升级编译器栈带来的是更高的代码生成质量与更广的语言/特性支持，而「更快重建」则直接改善日常体验。更值得注意的是，ROCm 建立在 LLVM 之上意味着它与整个开源编译生态共享上游成果：LLVM 的每一次优化、每一个新指令集支持，都会间接惠及 ROCm。这条策略对比封闭的专有编译器栈是一种明显的结构优势——它让「跟进硬件新特性」的成本大幅降低。对使用者的实际建议是：在选择异构计算平台时，除了看峰值性能，还应关注它的编译工具链是否建立在主流开源基础设施之上，因为这决定了它能否快速跟上硬件与新算子的演进。

关注理由：① 要理解「热页检测」为什么需要硬件协助，得先理解分层内存带来的新矛盾。所谓分层内存，是指服务器上同时存在多级内存：靠近 CPU 的普通 DRAM 快但贵且容量有限，通过 CXL 挂接的内存容量大但延迟高、带宽低。理想情况下，访问频繁的「热页」应当放在快的 DRAM 里，访问稀疏的「冷页」可以放在慢的大容量内存里，从而在成本与性能之间取得平衡。问题在于：谁来持续判断哪些页是热的，并在页面冷热变化时把它们搬来搬去？纯软件监测（如内核周期性扫描页表、统计访问）需要消耗相当多的 CPU 与内存带宽，而且采样精度受限于采样频率——扫描太快影响业务，扫描太慢则跟不上变化。这正是硬件采样的价值所在：把「谁在被访问」这件事交给 CPU 内部的采样电路去观察，开销极低，且粒度可达单次访问。
② IBS 的「基于指令的采样」这一机制，决定了它能给出比别人更细的信息——这一点值得展开。常见的硬件性能计数器通常是「聚合式」的：告诉你某个核心的缓存未命中率是多少，但不告诉你具体是哪条指令、哪个地址导致的。IBS 的思路不同：它以极低的概率随机选择一条正在执行的指令，把这条指令的完整上下文（地址、来源、目标、是否命中、走了哪条路径）记录下来。这样积累足够多次采样后，就能统计性地重建出「哪段代码、访问了哪些地址、数据从哪里来/到哪里去」的画像。把这种能力专门用于内存访问与 NUMA 节点追踪，恰好可以得到热页迁移最需要的信息：不只是「这个页很热」，还包括「访问它的是哪个核心、数据实际存放在哪个 NUMA 节点」。这条经验可以推广：在为某种自动优化（如迁移、缓存、调度）设计反馈信号时，应当优先选择那些「能回答具体问题」的细粒度信号，而不是只能反映总体状态的聚合指标——后者的可操作性通常很差。
③ 「设计上可跨不同 CPU / 厂商工作」这句话，是这条新闻里最具战略意味的部分，因为它决定的是这类技术能否成为公共基础设施。如果 IBS Memory Profiler 只服务于 AMD 自家 CPU，那么内核里对应的支持就会变成「针对单一厂商的私有路径」，难以获得维护者青睐，也难以被其他平台复用。而如果内核侧设计的是一个「与厂商无关的采样与热页提示接口」，各厂商只要提供对应的底层能力即可接入，那么这套机制就有可能进入主线、并长期存在。这与本期 Mesa 治理、RADV 移植等新闻背后的逻辑是同一个：Linux 生态中，一项技术能否被广泛采用，往往不取决于它的性能有多好，而取决于它是否被设计成「可被他人实现的通用机制」。对做底层库或平台接口的人，这是一个可以直接应用的取舍原则：在设计接口的第一天就假设「将来会有别的实现者」，把厂商特有的部分尽量压缩在最小、可替换的一层里。
④ 最后，这条新闻也提示了一个关于「性能」的重要转向：当硬件扩展越来越倾向于「堆容量」而非「堆速度」时，软件侧的自动数据放置会变得和算力同等重要。从 DDR 到 CXL、从本地显存到统一内存、从单路到多路 NUMA，硬件层面的「内存层级」正在变多，而每一层之间的带宽与延迟差距可达数倍。在这种结构下，同一套代码运行在同一台机器上，性能差异可能完全取决于「数据恰好被放在了哪一层」——这已经不是算法优化能解决的问题，而是需要系统级的自动管理。因此可以预判一个趋势：未来服务器性能的关键命题，会从「如何算得更快」越来越偏向「如何把数据放对位置」，而这类能力的实现离不开「硬件提供可观测性 + 内核提供自动决策」的配合。对使用者的现实建议是：在评估新平台时，除了关注核心数与频率，也应关注它是否提供「内存访问的可观测性与自动迁移能力」——在分层内存成为常态之后，这往往比单纯的算力指标更能决定实际吞吐。

关注理由：① EPP 是什么、为什么它值得用「每核动态调整」的方式去优化，是理解这项工作的前提。EPP（Energy Performance Preference）是 CPU 提供给硬件的一个「偏好旋钮」：它不指定具体频率，而是告诉处理器的电源管理固件「在性能与省电之间我更偏向哪一边」，由固件据此在给定负载下决定频率与电压。问题在于这个旋钮传统上是「全局或按策略」设定的：要么整机省电优先（续航长但爆发慢），要么性能优先（反应快但耗电）。而现代处理器的现实是：同一时刻，不同核心在干的活差别巨大——有的在跑游戏的主渲染线程（延迟敏感，希望立刻拉满频率），有的在做后台编译或解压（吞吐敏感，频率低一点也无所谓，省电更划算）。「为一颗近期待过忙的核心单独提高 EPP」的思路，正是把「全局旋钮」变成「按核心、按近期活跃度自适应」。
② 为什么它特别强调「帧时间尾部」这个指标？因为对游戏体验而言，最差的那些帧比平均帧更重要。平均帧率容易给人「游戏很流畅」的错觉，但真正让人感觉到卡顿的，是那些偶尔出现的、耗时极长的帧——它们会造成可见的顿挫。帧时间的「尾部」（如 1% low、0.1% low）正是用来描述这些最差帧的指标。它们的成因常常是「某个线程突然需要立刻满频运行，但处理器还停留在低功耗状态，需要一段时间才能升频」，这段「升频延迟」就体现为一次超长的帧。针对「近期繁忙的核心」做 EPP 提升，本质上是「提前把曾经忙碌的核心保持在较积极的状态」，从而缩短这类突发负载下的升频等待。这条经验对所有做性能优化的人都适用：当优化的目标是人机交互体验时，衡量标准应当是「最差情况」而非「平均情况」——平均值的改善可能完全无法被感知，而尾部的改善却直接决定「卡不卡」。
③ 评审要求把启发式「从驱动上移到 governor」，是一次教科书式的分层修正，值得关注它的理由。驱动（driver）的职责通常是「认识这块硬件、把它正确地驱动起来」；而 governor 的职责是「根据系统状态做策略决策」。把「近期是否繁忙 → 是否提高 EPP」这样的判断写在驱动里，会带来几个现实问题：一是策略与硬件细节耦合，难以独立演进；二是无法被别的平台复用；三是用户难以按需替换或调整策略。把它移到 governor 层后，策略就可以被独立地修改、测试和复用，甚至可以针对不同场景选择不同的 governor。这与本期 Mesa 治理、RADV 移植、IBS 跨厂商设计等新闻背后是同一套工程直觉：把「机制」与「策略」分开，让机制稳定、让策略可替换。这条原则可以推广到任何系统设计：当你在实现一个「判断什么情况下该怎么做」的逻辑时，先问自己「这段判断属于硬件适配，还是属于系统策略」——放错层次的代码，短期内能跑，长期一定会变成难以移除的耦合。
④ 最后，「让 Wine / Proton 提供线程提示」这个正在考虑的想法，指向了跨层协作中一个更普遍的机会与风险。要准确地做「这是游戏线程」这样的判断，最可靠的信息其实来自应用层——而 Wine / Proton 恰好位于「Windows 游戏」与「Linux 系统」之间，它知道哪些是渲染线程、哪些是音频线程。让运行层把这类信息以「提示」的形式传给内核调度，理论上可以让电源管理做得更精准。但风险也同样清楚：一旦系统行为依赖应用/兼容层提供的提示，就必须回答「提示不可信、或不提供时怎么办」——否则会演变成「只有被特别适配过的软件才表现好」的碎片化局面。因此一个成熟的方案应当把提示视为「优化而非依赖」：不提供提示时退回到通用启发式（这也是为什么主体思路仍是「让 governor 依据系统状态自行判断」）。对做平台的人的启示是：引入来自上层的「提示」通道时，务必同时设计好「缺失提示时的降级行为」，并在设计上明确「提示只能带来更好的结果，不能成为正确性的前提」——这决定了系统是「对所有人都不错」，还是「只对适配过的人不错」。

高通为 ZRAM 提交 QPaCE 硬件加速驱动：Snapdragon 8 Elite Gen 6「Hawi」内置页压缩引擎，初版聚焦低延迟同步单页路径并引入 qpace-lz4 后端，基于 ring 的异步高吞吐路径尚未实现
计算 compute 内核 kernel
高通 Snapdragon 8 Elite Gen 6「Hawi」SoC 内置了一个硬件加速器——Qualcomm Page Compression Engine「QPaCE」。近日公开的 Linux 补丁为该引擎提供了驱动，用于为 ZRAM 块设备加速页压缩与解压。
补丁要点
· 引入 QPaCE Linux 支持的补丁说明该硬件块出现在高通的新款 SoC 上；
· 目前的补丁仅将其添加到 Hawi SoC（即 Snapdragon 8 Elite Gen 6）的设备树中；
· 对 Linux 的 ZRAM——作为存在于物理内存中的压缩块设备（例如用于压缩交换）——QPaCE 能提供低延迟、更快的压缩与解压性能。
当前实现的范围与限制
· 初版 QPaCE Linux 驱动聚焦于该引擎的「urgent」同步路径，面向低延迟的单页操作；
· 该硬件同样具备基于 ring 的异步操作能力，可用于高吞吐的批量压缩，但初版 Linux 驱动尚未实现这一点；
· 补丁引入了一个新的 qpace-lz4 Zcomp 后端，通过该硬件进行压缩 / 解压。
相关补丁系列见 内核邮件列表。
关注理由：① 要理解「为 ZRAM 加速压缩」为什么值得开发一颗专用硬件，得先看清 ZRAM 在现代系统里扮演的角色。ZRAM 的思路是：在物理内存里划出一块区域，当作「压缩后的块设备」使用——写入的数据先被压缩再存放，读取时再解压。它最常见的用途是压缩交换（compressed swap）。这样做的好处是：当物理内存紧张时，系统可以把不常用的页压缩后留在内存里，而不必把它们写到速度慢几个数量级的闪存上。这个取舍有两层价值：一是速度快得多（内存 vs 存储），二是避免了闪存写入带来的磨损与寿命消耗——后者对移动设备尤其重要。而它的代价完全落在一个地方：CPU。每一次换出与换入，都要做一次压缩或解压，这消耗的不只是算力，还有内存带宽。在手机上，内存带宽与功耗恰恰是最稀缺的两项资源。
② 因此「把压缩卸载到专用硬件」这件事，在移动端的经济账是算得过来的——这解释了高通为什么专门做一颗 QPaCE。通用 CPU 做 LZ4 之类的压缩当然很快，但它的能耗效率远不如一块为压缩量身定做的固定功能电路。而且，让 CPU 从压缩任务中解放出来，还能顺带降低整机的热压力——在手机这种散热受限的形态里，省下的每一瓦热预算都可以转给 CPU/GPU 去跑真正的工作。这类「用固定功能硬件替代通用 CPU 做高频重复任务」的做法，正是现代 SoC 设计的核心思路之一（编码器、DSP、NPU 都是同一逻辑）。由此可以提炼一条判断规则：当某项操作「出现频率极高、算法固定、且结果有明确定义」时，就具备了硬件卸载的条件；反过来，如果算法仍在快速演进或需要频繁改逻辑，则不适合固化为硬件（因为硬件难以修改）。压缩算法之所以适合，正是因为 LZ4 这类算法已经高度标准化。
③ 「初版只做同步单页路径、异步 ring 路径尚未实现」这个取舍，是一份很典型的「先争取低垂果实」的工程路径，但它同时意味着性能收益是有上限的。同步单页路径的特点是逻辑简单、延迟确定性好：收到一个页面的压缩请求，引擎处理完立即返回——这对「换页」这类需要尽快完成、且单次数据量很小的场景非常合适。而基于 ring 的异步路径则面向「批量提交、高吞吐」：一次性把大量页面丢进队列，引擎流水线处理。先实现前者是合理的——它风险小、能立即覆盖最常见的使用模式；但它也意味着「批量压缩」这一最能体现硬件吞吐优势的场景暂时享受不到收益。这条经验对所有做硬件加速或异步改造的人都有用：这类工作的收益通常不是一步到位的，而是随「异步程度」逐级释放的；因此在评估时应当区分「当前版本能拿到多少」与「设计潜力有多大」，不要因为首版收益有限就否定方向，也不要因为宣称「支持硬件加速」就默认已拿到全部收益。
④ 从整条新闻的形态看，它清晰地展示了一个「新硬件能力进入 Linux 支持」的标准流程，而这套流程本身对使用者的期待管理很有价值。注意当前状态：补丁刚发到邮件列表、只添加到一款 SoC 的设备树、只实现了同步路径、需要新后端（qpace-lz4）才能生效——这意味着距离普通用户「开箱即用」还有相当距离：它先要经过代码评审，再进入内核版本，然后才能被发行版/厂商固件采用。与此同时，它还需要软件侧的配合（例如 ZRAM 要选择 lz4 后端，才可能走到这条硬件路径上），也就是说「硬件支持」与「默认启用」是两件事。这对关注新平台的用户来说是一条实用提醒：当看到「某 SoC 新增了硬件加速器支持」时，合理的预期是「它会在未来一到两个内核周期内变得可用，并且初期通常是可选的、需要手动配置的」，而不是「立刻就能享受」。判断进度最可靠的信号，不是新闻标题，而是「补丁是否已被合入、以及它是否出现在设备树之外的默认配置里」。

关注理由：① 这条改动的分量不在「多了个功能」，而在「兼容层从用户的显式决策变成了系统的默认行为」。在此之前，Proton 在 Linux 上其实一直有个身份上的裂缝：Steam 商店里的游戏由 Valve 自动决定用不用 Proton、用哪个版本，而用户自己添加的 Windows 程序则被当作「不知道怎么办」的东西，需要用户手动去属性里指定。把默认值翻过来，意味着 Valve 愿意为非商店内容（也就是自己无法预筛、无法预验证的那部分）兜底。判断一个兼容层的成熟度，比「又修好了哪款游戏」更可靠的信号，恰恰是它是否敢于成为默认——因为默认意味着要为最坏情况负责。这也解释了为什么这类改动通常先在 Beta 通道出现：它改变的是所有用户的行为，一旦出问题，面比单个游戏的回归大得多。
② 从机制上看，这条新闻给出的是一次「同样的栈，更大的适用范围」的扩张，而不是新造了一层东西。非 Steam 程序与商店游戏走的是同一条路径：DXVK 与 VKD3D-Proton 把 Direct3D 调用翻译成 Vulkan，再交给 Mesa/RADV、NVK 或 NVIDIA 专有驱动；Steam Linux Runtime 容器则把发行版之间的库版本差异挡在外面。也就是说，这次变化在技术上是「零新增组件」的——它的价值来自于把这套已经为商店游戏验证过的栈，开放给用户自带的任意 exe。值得注意的是，这类「扩大适用范围」的改动往往并不显眼，但它对生态的实际推动常常大于某个具体特性的优化：因为它降低的是「尝试」的成本，而门槛降下来之后，愿意把 Linux 当主平台的人才会变多。
③ 把这一条与本期第 1 条 NVIDIA 615.78.08（VK_NV_low_latency2 第 3 版、修 The Last of Us Part II 方块损坏、修 >2GB GPU 页表分配失败）放在一起看，可以读出 Linux 游戏栈「分层推进」的节奏。驱动与扩展层在解决「跑得更好」的问题——延迟、画面损坏、显存管理；而客户端与运行时层在解决「更容易跑起来」的问题——默认值、容器、库环境。这两条线缺一不可：只有前者，用户仍要自己摸索配置；只有后者，跑起来了却体验不佳。当两类改进同时出现、并且方向都指向「减少人工干预」时，通常说明这个平台已经越过了「极客自娱」的阶段，正在往可长期日常使用的方向走。
④ 最后一个实用的边界提醒：把默认值改成 Proton，并不等于「所有非 Steam 的 Windows 程序都能跑」。Proton 走的是 API 映射（translation）而不是整机模拟，因此对带内核态反作弊、依赖私有驱动、或深度依赖 Windows 特有服务的程序（部分 DRM、某些专业套件、多数竞技类网游）依然无能为力；此外，默认值只在 Beta 通道先行，正式版才会跟进，而且用户随时可以在「属性 → 兼容性」里把它改回原样、或强制指定某个 Proton 版本 / Steam Linux Runtime。所以合理的预期是「自己添加的小工具、老游戏、独立作品这类程序，开箱即用的概率明显提高了」，而不是「Linux 可以跑一切 Windows 软件了」。
