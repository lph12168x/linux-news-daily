Intel 为 Steam Play (Proton) 推进 XMX 加速的 XeSS：Intel 显卡上的超分走专用矩阵引擎
图形 GPU
Intel 工程师为 Valve 的 Proton (Steam Play) 提交了引入 XeSS 支持的 PR，并附带 VKD3D-Proton 与 DXVK 的配套改动。
方案：在 Proton 内置 libxess.dll，把游戏的 XeSS Direct3D 12 调用转发给 Linux 侧 XeSS 库，从而在 Intel 图形硬件上启用 XMX 矩阵引擎加速路径，而不是回退到更慢的通用 DP4a 路径。
配套改动：VKD3D-Proton 侧启用 XeSS 所需的 Vulkan 扩展与特性（借助其互操作接口把 D3D12 对象转成 Vulkan）；DXVK 侧则是在 XeSS 由 Proton 提供时不再隐藏 Intel GPU 的品牌标识（XeSS 依赖厂商识别选择路径）。
目前尚未合并，详见 ValveSoftware/wine PR #369；参照 AMD FSR / NVIDIA DLSS 在 Proton 的同类工作，预计会适时合入。
关注理由：Intel 独显/核显跑 Windows 游戏的画质-性能短板正在被补齐：此前 XeSS 在 Proton 下走不到 XMX，超分效果与 AMD/NVIDIA 阵营不对等。
这也是「厂商超分 API → Proton 转发层」模式的又一实例（继 FSR、DLSS 之后），对关注游戏图形栈、D3D12-on-Vulkan 转换层的同学是现成参考；Intel GPU D 系列（Crescent Island）主打 AI 推理，XMX 路径的打通对其游戏侧卖点同样关键。

Linus 的 AI 内核代码被 Meta 工程师重做：page cache 无 folio 引用读取实测性能大涨
内核 kernel
上周报道过 Linus Torvalds 用 Claude Code 推进的内核优化分支（noref-filemap-read：从 page cache 读取时不持有 folio 引用，缓解多线程小读同一文件的引用计数争用）。本周 Meta 工程师 Kiryl Shutsemau 把这套代码重做并正式发到 LKML。
原理：多 CPU 线程对同一文件做小读取时，filemap_read() 都要取/放同一个 folio 的引用，refcount 在 CPU 间反复弹跳；新方案让 filemap_read() 与 shmem 直接从 page cache 拷贝而不取引用，此类 folio 改为经一个 RCU 宽限期后才释放。
实测：在 Threadripper 上以 64 线程对比 EXT4 / TMPFS / XFS 与裸块设备、开关默认 CPU 安全缓解各测一轮，成绩「相当可观」（Phoronix 称 fabulous improvement）。补丁仍为 RFC，尚有设计问题待解决，补丁系列见 LKML。
关注理由：这是 10-12 期「Linus 用 AI 推进内核改进」故事的实质性续集：RFC 代码被资深 MM 工程师接手重写成正式补丁系列，「AI 起点 + 人类专家收尾」的协作模式越来越清晰。
技术上，无引用 page cache 读取 + RCU 延迟释放是 MM 子系统少有的读取路径结构性优化；对高并发小 I/O 读场景（数据库、对象存储元数据、AI 数据加载）都有潜在收益，值得跟踪其转正进度。

GNOME Mutter 合入省电模式 GPU 负载修复：显示器休眠时客户端不再空转渲染
显示 display
一个月前 GNOME 51 收到缺陷报告：显示器休眠期间 GPU 占用居高不下——客户端仍在持续渲染。Red Hat 的 Jonas Ådahl 定位到根因：省电模式下 CRTC 后端 stage view 的重绘未被节流。
17 个补丁今日合入 Mutter（MR !5363）：渲染器在省电状态且 stage view 面向 CRTC 时主动抑制绘制；vkgears / glxgears / es2gears 在省电时仍正常上报约 60 fps，但 frame clock 无需感知省电状态；同时处理被丢弃帧的 presentation feedback 迁移，让客户端正确收到 .discarded 事件。
代码已进 Mutter 主线，将随 GNOME 51.2 发布。
关注理由：笔记本「合盖/息屏后风扇狂转、电量偷跑」的常见元凶之一就是合成器未节流的空渲染，这是一个面向功耗的显示栈修复，对 OLED/高端屏的烧屏防护与整机续航都有意义。
对做合成器/显示方向的同学，补丁展示了「presentation feedback 与省电路径协同」的正确姿势；这类「CRTC 状态 → 渲染抑制 → 反馈事件」的联动逻辑也可对照 zeus 平台的显示低功耗设计。

RADV 对 RDNA1 (GFX10) 默认启用 VK_EXT_host_image_copy，GFX9 获实验支持
图形 GPU
AMD 开源 Vulkan 驱动 RADV 的 VK_EXT_host_image_copy 支持再扩面（MR !42475，Wei Zhao，进 Mesa 27.0）：
① GFX10（RDNA1，Navi 1x）默认启用该扩展——此前默认启用范围是 GFX10.3（RDNA2）及更新；此前阻碍 Navi 1x 默认开启的回归已解决；
② 同一 MR 还为 GFX9（RX Vega / Radeon VII 一代）带来实验性支持（沿用环境变量开启）。
背景：host image copy 允许主机内存与 Vulkan 图像之间直接拷贝，减少中转开销，对核显（iGPU）尤其有利；RADV 的实验性 HIC 支持始于 2025 年 7 月。
关注理由：对老卡用户是实打实的收益：RDNA1 默认可走 host image copy，上传纹理类工作负载开销更低；GFX9 实验支持则把这份红利试探性下探到 Vega 世代。
对做驱动/图形栈的同学，这也提示 host image copy 在 UMA/iGPU 场景的价值——与 zeus 这类集成平台「CPU/GPU 共享内存零拷贝」的设计思路相通，可以研究 RADV 在不同显存类型下的 HIC 实现。

SpacemiT 发布服务器级 RISC-V 处理器 V100：46 核混合架构，宣称首款完整符合 RISC-V 服务器规范
计算 compute
继面向桌面/开发的 K3（RVA23）之后，SpacemiT（进迭时空）发布 V100 服务器级 RISC-V 处理器，宣称是首款完整符合 RISC-V 服务器规范的芯片（含 UEFI、ACPI、SMBIOS 等）。
规格：46 核混合微架构——6 个 香山（XiangShan）昆明湖 V2R2 核心 + 40 个 SpacemiT X100 核心；频率 2.2~2.4GHz；12nm 工艺；TDP 120W；八通道 DDR5-4800；PCIe 5.0 共 52 lanes；单服务器支持双路（合计 92 核）。
客观看：2026 年的 12nm / 52-lane PCIe 5.0 服务器 CPU 与 Xeon / EPYC 甚至 Arm 服务器平台存在代差，但其「借 AI 热点入场 + 完整服务器规范兼容」的路线值得关注。
关注理由：RISC-V 服务器路线的标志性事件：UEFI/ACPI/SMBIOS 全兼容意味着现有 Linux 发行版与系统软件栈（含 Edk2、ACPI 表解析、固件启动链）可以直接对齐，而不是各玩各的。
「香山大核 + 自研小核」的混合架构也值得留意——与 Arm big.LITTLE 类似的异构组合出现在服务器 RISC-V 上，后续内核调度（EAS/EPP）如何适配是看点；Ubuntu 26.10 刚首次提供 RISC-V 桌面镜像，生态在快速补位。

AMD GAIA 0.25 发布：Ryzen AI 本地 AI Agent 工具链多项改进
NPU
AMD 开源项目 GAIA（现定位「AMD 的开源 agent 工厂」）发布 0.25 版，面向在 Ryzen AI 硬件（含 NPU）上构建/运行本地 AI Agent：
① gaia chat 默认改用旗舰 GAIA agent（替代已退役的 ChatAgent）；
② gaia talk 语音转录与合成改走 AMD Lemonade 本地 AI 服务器（后端 Whisper + kokoro-v1）；
③ Windows 下 Python 环境从约 0.9GB 瘦身到约 0.1GB（移除不必要依赖）；
④ 修复 16GB 内存笔记本首次启动即 OOM 被内核杀掉的老问题——现在加载模型前先检查可用内存、动态收缩上下文窗口；
⑤ 一批针对 Strix Halo 的优化与 agent/模型改进。
关注理由：AMD 在「本地 AI Agent 运行时」这一层的开源投入在加速：GAIA + Lemonade（推理服务）+ Ryzen AI NPU 构成端侧 agent 的完整栈，与 Intel 的 OpenVINO/NPU 驱动路线对标。
对我们关注的 NPU 软件栈，「模型加载前按可用内存收缩上下文」这类资源感知的 agent 调度细节，以及 Strix Halo（大 GTT 池 APU）的优化取向，都可作为端侧 NPU 部署的参考实践。
