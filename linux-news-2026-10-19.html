Linux 7.3 正式发布：I/O 提速、AMD Zen 6 准备、Valve 贡献满满，7.4 合并窗口随即打开
内核 kernel
Linus Torvalds 按期发布 Linux 7.3 稳定版内核（10-18 周日）。本期亮点：
① 现代系统 I/O 性能提升（NVMe/IO_uring 路径多处优化）；
② AMD Zen 6 平台准备（BTB 上下文隔离等一系列使能工作）；
③ Steam Controller 2026 内核驱动支持等来自 Valve 的大量贡献；
④ 老款 AMD GPU 改进、小显存系统的 vRAM 管理改进；
⑤ 发布前收尾修复：2024 年以来的偶发 SMP 启动挂死、三星 990 PRO / 990 EVO Plus SSD 固件虚报能力的 workaround，以及 XFS 维护者 Darrick Wong 服务 23 年后宣布暂退。
7.3 发布即开启 Linux 7.4 合并窗口；若 7.4 仍按期在 12 月底发布，它有望成为今年的 LTS，否则 Greg KH 可能保守地钦点 7.3 为年度 LTS。完整特性清单见 Phoronix 的 7.3 features 汇总页。
关注理由：内核版本例行大事件：7.3 正是过去两周大量 AMD/Intel 图形、调度与 I/O 优化的载体，各发行版（如 Ubuntu 26.10）也刚以它为基线出货。
「7.3 还是 7.4 当 LTS」的悬念值得跟踪——影响未来一年生产环境内核选型；对关注 RDMA/存储 I/O 的场景，7.3 的 I/O 提速点与 7.4 合并窗口里的 do_open() +39%、sheaf 预填充等改动都在同一条性能主线上。

Linux 7.4 特性预览：Radeon HDMI 2.1 默认启用、AMD PerfOpt 默认开、Apple M4 设备树进入主线
内核 kernel 图形 GPU
7.3 发布后 7.4 合并窗口打开，Phoronix 汇总已排队/已合入的重磅特性：
AMD 方向：AMDGPU HDMI 2.1 默认启用（VRR/ALLM 到位，FRL 补齐）；AMD PerfOpt IOMMU 默认开启——核显 AI/LLM 推理实测最高 18~23% 提升，且前代 Ryzen APU 同样受益；Zen 6 继续加码（BTB CTX 隔离、RMPOPT、P-State 调优）；Ryzen AI Max 400 的 Gorgon Halo NPU 补上 AMDXDNA 设备 ID。
Intel 方向：Battlemage CPU binds + 迁移队列 ULLS、Xe 驱动 vRAM 健康检查与坏页降级处理、Rugged Panther Lake 准备、BFF 驱动合入；Nova 驱动持续扩建。
Apple/其他：Apple M4 与 A18 Pro 首批设备树进主线（可启动但尚不可用）、Apple Silicon 音频上游化、Google Tensor G5/Pixel 10 主线支持、树莓派 10 英寸 Touch Display 2、Snapdragon X2 笔电使能。
性能/其他：EXT4 iomap 缓冲 I/O 路径、FUSE 大 folio、Intel Instruction Timeout 防 TDX VM DoS、steal governor、AVX-512 优化 xor_gen、内核构建提速补丁、C 版 Binder 驱动移除（转 Rust）。
关注理由：7.4 就是「下一个该盯的内核」：AMDGPU HDMI 2.1 默认开 + PerfOpt 默认开，是 Radeon 用户体感最强的两个开关；Xe vRAM 健康检查则是 Intel 独显可靠性的基础设施级改进。
预计 12 月底发布且有望成为年度 LTS——对生产内核升级规划直接相关。

Mesa Zink 在 Vulkan Video 之上实现 VA-API 视频加速，随 Mesa 27.0 落地
图形 GPU 显示 display
Mesa 合入 通用 Zink Gallium3D 驱动的视频加速支持：在 Vulkan Video 接口之上实现 VA-API，让面向通用 Linux VA-API 接口的应用最终能借 Vulkan Video 获得视频硬解加速。
这是 Valve 的 Mike Blumenkrantz 与 Red Hat 的 David Airlie 持续数年的项目（MR !31517），代码已合入，将出现在 Mesa 27.0（明年 Q1）。
现状：目前仅支持 H.264 解码，尚无其他格式；测试主要在 RADV（Radeon Vulkan）驱动上进行；H.265 与 AV1 的视频加速代码在开发中、尚未合入。
关注理由：「VA-API on Vulkan Video」一旦成熟，意味着视频硬解不再依赖每家驱动的独立 UVD/VCN 后端——一个 Vulkan 驱动即可同时承载图形与视频解码，对 Zink 生态（Steam Frame 的 OpenGL、NVK、Asahi 等）是拼图式补全。
对做显示/多媒体管线的同学，这是观察视频栈向 Vulkan 统一趋势的关键落点；H.265/AV1 合入节奏值得持续跟踪。

AI 复活 Mesa LLVMpipe 的 AVX-512 支持：David Airlie 借大模型补完多年未竟的 512 位着色器路径
图形 GPU 计算 compute
Red Hat 工程师 David Airlie 提交 draft MR（!45279）：为 LLVMpipe（CPU 软渲染 Gallium3D/OpenGL 驱动）的片元着色器添加 512 位宽向量支持，即 AVX-512 路径。
背景：Airlie 几年前曾尝试为 LLVMpipe 做 AVX-512 但未能完成；近日借助 GPT Terra 与 Astra AI 模型，用 AI 补齐代码最后的缺口并顺带揪出若干 bug，最终成稿。
注意点：Airlie 自己没有 AVX-512 硬件，因此尚未实测；代码正确性仍待社区验证（这也是 draft 状态的原因）。细节见其博客「Jetlag Diversions: llvmpipe 512-wide」。
关注理由：又一个「AI 补完驱动/编译器底层代码」的标志性案例——与前日 Claude Code 逆向硬件写驱动、内核 agents/ 目录等动态同一趋势线。
LLVMpipe 是无 GPU 环境（云桌面、CI、虚拟化）的兜底渲染路径，AVX-512 落地将直接抬高软件渲染基线；等有 AVX-512 机器的社区跑出实测数据后，值得回头核对收益幅度。

X.Org 客户端库再曝 17 个安全漏洞：libX11 / libXi / libXpm / libXrender / libXtst 均发修复版
显示 display
距上次 X.Org Server / XWayland 12 个漏洞披露不到两周，X.Org 客户端库再公开 17 个安全漏洞，影响：
① libX11（核心 X11 库）→ 修复版 1.8.14；
② libXi（X Input 扩展）→ 1.8.4；
③ libXpm（X Pixmap 格式）→ 3.5.20；
④ libXrender（RENDER 扩展）→ 0.9.13；
⑤ libXtst（TEST 扩展）→ 1.2.6。
漏洞类型以越界读写、堆缓冲区溢出为主，部分可致拒绝服务；由多位研究员分别发现，细节见 X.Org 邮件列表。
关注理由：X.Org 生态两周内连爆 29 个漏洞（12 服务端 + 17 客户端库），暴露出这批上古 C 代码库的维护短板；对仍在跑 X11 会话/远程转发的环境，五个库都建议尽快升到修复版。
结合上期 X.Org Server 26.1 RC、XWayland 移除 EGLStream 等动态，X11 栈「修修补补维持存量」的现状愈发明显——迁移 Wayland 的长期路线不变。

Intel LLM-Scaler-vLLM PV 1.5 发布：vLLM 0.14 直跳 0.26，Arc 独显跑大模型体验大幅改善
计算 compute
Intel 发布 LLM-Scaler-vLLM PV 1.5——面向 Arc 独显的容器化 vLLM 推理栈（源自 Project Battlematrix），为即将到来的 Crescent Island / GPU D 系列铺路。主要更新：
① vLLM 0.14 → 0.26 大版本跨越（上游现为 0.31，仍在追赶）；PyTorch 2.10 → 2.12；
② 模型覆盖扩大：Qwen3.6-27B / Qwen3.8-27B / Qwen3.6-35B-A3B、gemma-4-26B-A4B-it / gemma-4-31B-it；
③ 支持在线 FP8 与对称 INT4 量化、FP8 KV cache；
④ Qwen/Gemma 4 的首 token 延迟（TTFT）改善、MTP 解码性能提升、LoRA 服务与 FP8 KV cache 性能优化；
⑤ 一批 bug 修复。发布页见 GitHub intel/llm-scaler vllm-1.5。
关注理由：Intel 在 GPU D 系列（agentic AI 推理定位）上市前把软件栈追平到 vLLM 0.26 + FP8/INT4 量化，补齐了 Arc 独显跑大模型的最大短板（软件生态滞后）。
对做 Intel GPU 推理选型的场景，现在 Arc Pro B60/B70 + LLM-Scaler 是可评估的低成本路线；D 系列发布后的软件成熟度可据此预判。

实测：Linux 7.3 再为 96 核 Threadripper PRO 9995WX 榨出更多性能
计算 compute
Phoronix 在 96 核 / 192 线程的 AMD Ryzen Threadripper PRO 9995WX（Zen 5，TRX50 平台）上，对比 Linux 7.2 vs 7.3 Git 跑了一轮基准：7.3 在多数项目上继续小幅领先。
亮点：Flexible I/O Tester（IO_uring 随机读，Direct 与 buffered 两种模式均最快）；PostgreSQL（500/800 客户端读写，吞吐与平均延迟均优）；MariaDB oltp_read_only；金融数据库 TigerBeetle；网络基准（TCP/QUIC/UDP）；内核微基准（fork、IO_uring、mutex）；内核与 Godot 编译持续小幅变快；CPU 侧 AI 负载（Lemonade MiniCPM4-8B）也有小幅收益。
关注理由：与 7.3 正式发布同日发出的性能佐证：I/O 与调度优化对高核数 HEDT/工作站平台是普惠的，尤其是 NVMe + IO_uring 与数据库负载。
对 Threadripper/EPYC 工作站用户，7.3 值得列入近期升级计划；Phoronix 后续还会有 EPYC 侧的 7.3 对照实测可跟踪。

Servo 0.6 落地 CSS Grid 支持，实验性 Threadboost 让 Speedometer 提分 50%
显示 display
Rust 编写的开源浏览器引擎 Servo 公布 8 月进展报告（随 Servo 0.6 与 Servoshell 演示浏览器）：
① CSS Grid 支持落地——大量网站布局自此能在 Servo 上正确渲染，是兼容性的分水岭；

⑤ 实验性 Threadboost 调度特性使 Speedometer 基准提升约 50%。
关注理由：CSS Grid + Threadboost 两项一起看：Servo 正从「技术演示」走向「可用引擎」——布局兼容性补齐后，剩下的是性能与生态。
对做嵌入式 GUI / 轻量 WebView（如用 Servo 替代 Chromium 的场景）的同学，0.6 是值得重新评估的节点；Threadboost 的线程调度思路（把渲染管线任务优先级化）也有借鉴价值。

Intel TDX 其实不需要那么多缓存刷新：内核将移除多余的软件 flush 路径
计算 compute
Intel 机密计算 TDX（Trust Domain Extensions） 的内核实现中，长期以来在 MKTME 不同 KeyID（AES 密钥）之间迁移内存时执行软件驱动的缓存刷新——这是早期 TDX 架构假设硬件需要 VMM 协助而留下的遗产。
Intel 工程师 Rick Edgecombe 的补丁系列「Drop unneeded cache flushing」指出：所有已定稿的 TDX 硬件（Sapphire Rapids 起，Emerald Rapids 起全系 Xeon 支持）实际都能自行处理 KeyID 迁移的缓存一致性问题，只是 Intel 文档从未更新；TDX 架构文档将在下一版修订更正，Linux 内核随之删除多余的软件 flush 代码。
结果：内核代码更简单；补丁说明未声称明确的性能收益（减少 flush 理论上对 VM 生命周期操作有正贡献）。
关注理由：机密计算（SEV-SNP / TDX）是云上 GPU/NPU 资源隔离的基石方向；这类「清掉历史包袱」的补丁能简化 TDX 内核路径，对理解 TDX 的内存加密生命周期（KeyID 迁移语义）是很好的参考材料。
顺带跟踪：7.4 还在合入 Intel Instruction Timeout（Notify VM Exit）防 TDX VM DoS，两件事同属 TDX 硬化主线。

Wine 11.20 发布：CD-ROM 支持迁入 Mount Manager，ARM64EC 支持回放调试
显示 display
Wine 11.20 双周开发版发布（向 2027 年初的 Wine 12.0 稳定版冲刺）：
① CD-ROM 支持代码迁入 Mount Manager——NTDLL 重构的一部分，不再直接打开 Unix 设备，改走 mountmgr；
② ARM64EC 支持继续推进，新增回放调试（replay debugging）能力；
③ XML 校验改进；
④ 24 个 bug 修复，覆盖 QuickBooks 到 Battlefield 1942、Pure Pinball 等应用与游戏。
关注理由：Wine/Proton 是 Linux 游戏与 Windows 应用的地基，双周版里 ARM64EC 回放调试对 Windows-on-ARM 兼容层开发是实打实的工具链改进；设备访问全面走 Mount Manager 也是底层架构清理的一步。
对 Steam Deck / Steam Frame 生态，Wine 12.0（明年年初）的进展决定了下一轮 Proton 底座的时间表。
