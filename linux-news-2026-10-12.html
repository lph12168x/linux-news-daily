Linus Torvalds 用 Claude Code 推进内核大改进：读 page cache 不再持有 folio 引用
内核 kernel
Linus Torvalds 在自己的 torvalds/linux.git 里新建了一个不寻常的分支 noref-filemap-read-with-llm —— 他平时基本只维护 master、很少开分支，而分支名里的「LLM」后缀直接点明了来历。
该系列要解决的是一个具体瓶颈：多线程对同一个文件做小尺寸读取时，会在 folio 引用计数上激烈竞争。目标是让 page cache 的读取路径不再需要持有 folio 引用。
Linus 在补丁说明里明确承认了 AI 的参与：「上面的代码、测试程序、评审，以及本文初稿，都是我指导下由 LLM 编码助手（Claude Code）完成的；测量则在我自己的机器上跑。」
目前补丁停留在该分支上，是否赶上下一个 Linux 7.4 合并窗口尚待观察。
关注理由：这是内核上游第一次由 Linus 本人带头发起、并公开署名「AI 参与」的核心内存管理改进。过去他反复强调 AI 产物需要人工把关，这次他亲自下场，等于亲手划出一条可参考的边界：方向由人定、代码与测试可由 AI 起草、最终由人验证。
技术层面同样值得重视——「不带 folio 引用读 page cache」如果成立，海量小读并发场景（数据库、文件服务、构建系统、AI 数据加载）的锁竞争会显著下降。这是能直接反映到吞吐上的底层改动，而不是又一个驱动 quirk。

Linux 合入 AMD TLBI Erratum #1718 内核规避补丁
内核 kernel
AMD TLBI（地址转换缓存失效）勘误 #1718 此前只能靠 CPU 微码修复：部分 Zen 处理器在执行 INVLPGB / TLBSYNC 指令对时可能失效失败，留下过期的页表翻译项。
对于尚未更新微码的受影响机器，内核现在补上软件规避——强制补一次 TLBSYNC，确保 TLB 项被正确失效。
该修复随 Linux 7.3-rc7 的 x86 修复拉取请求进入主线，并将回移到近两年内的受支持内核分支。
背景：自 2024 年末起，Linux 内核已在 TLB 刷写路径中使用 AMD 的 INVLPGB 指令来提升性能，因此这批 CPU 上的正确性尤为关键。
关注理由：INVLPGB 是 AMD 近两年内核性能优化的关键一环（此前 Phoronix 实测过它的收益，内核侧对 TLB 刷写做了大幅提速）。这次勘误说明硬件路径并非总可靠：一旦失效失败，就可能出现「读到陈旧内存」这类极难复现、却又直接破坏正确性的错误。
对内核对未刷微码机器的兜底，直接决定了大规模虚拟化与内存密集负载下能否放心使用这条快路径。凡是在 Zen 平台跑数据库、虚拟机或大内存作业，都值得同时确认微码与内核版本是否已含该规避。

微软为 Linux 贡献 Hyper-V 半虚拟化 IOMMU 驱动（目标 Linux 7.4）
内核 kernel
微软为 Linux 7.4 提交了新的 hv-iommu-guest 半虚拟化 IOMMU 驱动，已进入 IOMMU 子系统的 next 分支，由新增的 HYPERV_PVIOMMU 内核配置项启用。
它让 Hyper-V 上的 Linux 客户机获得内核对已分配设备的 DMA 保护，并支持把设备直通到客户机用户态（例如经由 VFIO）。
该驱动同时适用于 Intel VT-d 与 AMD IOMMU 平台：微软已用直通 NVMe 设备完成验证，Intel 侧还把 DSA 加速器直通到 Linux 客户机做了测试。
这套补丁的 RFC 最早可追溯到 2023 年 12 月，到 7.4 稳定版（预计 2026 年底）时刚好接近三年。代码将留在 next 分支，等待本月晚些时候 7.4 合并窗口开启。
关注理由：传统上 Linux 跑在 Hyper-V 上做设备直通时，DMA 保护与安全隔离一直是短板。这个驱动把 IOMMU 语义虚拟化后交还给客户机内核，使 Hyper-V 上的 Linux 虚拟机在安全属性上更接近裸机——对云端多租户与机密计算场景尤为重要，也让「Windows 宿主 + Linux 客户机」这一常见开发/计算组合更可信。
与此同时，IOMMU 子系统在 7.4 周期还收下了 AMD PerfOpt，两件事叠加说明 IOMMU 正在从「能用」走向「既安全又不拖性能」。

自动向量化 RISC-V Linux 内核初见成效：LZ4 最高 +15%，Btrfs +8.4%
计算 compute
RISC-V 内核构建目前并未使用该 ISA 的 Vector 扩展。Andy Chiu 在 LPC 2026 上展示了借编译器自动向量化的实验结果：对 crypto、RAID、XOR、user-copy 这类内核用例，Vector 能力可带来可观提速——
· LZ4 最高 +15%
· Btrfs 最高 +8.4%
· XFS 最高 +5%
· Nginx 负载最高 +2%
代价同样明确：内核自此依赖 Vector 单元，构建的可移植性下降；启用 Vector 需要额外的上下文管理开销与更多内存；内核态使用 FPU / 向量本就属于「禁区」；而要拿到最佳收益，还需按 CPU 逐个做编译器定向（per-CPU tuning）。
关注理由：这与 x86 侧当年「内核要不要启用 AVX-512」的取舍几乎同构——收益真实，但可移植性、上下文切换与功耗的代价同样真实。RISC-V 正从「能启动」走向「性能可竞争」，而压缩、校验和、拷贝这些热路径拿到两位数提升，会直接影响发行版是否愿意推出向量优化内核。
关注这场讨论，有助于判断 RISC-V 在服务器与边缘设备上的实际可用性拐点何时到来。

KNOD 推进：用 GPU 承担内核网络包处理，XDP 已达约 7000 万包/秒
计算 compute 内核 kernel
KNOD 项目在 LPC 2026（布拉格）介绍了最新进展。其思路是把 XDP 程序 JIT 编译成 GPU 机器码，网卡把数据包直接投递到 GPU 可访问内存，再由 GPU 处理——用通用显卡替代专用网络加速硬件，成本更低且能效更好。近期还新增了 RX IPsec 能力。
实测数据：在消费级显卡上，XDP 负载可达 约 7000 万包/秒，RX IPsec 达 80 Gbit/s；开发者认为其成本效益优于纯 CPU 处理，且更省电。
路线图：此前主攻 AMD 独显，接下来将探索 Intel Arc 显卡支持，同时确认可配合 Broadcom 与 Intel 网卡，并把 AMD 核显（而非仅独显）纳入探索范围。
关注理由：GPU 直连网络是近年内核数据面最激进的方向之一：把包处理搬到与显存同侧，绕开 CPU 与 PCIe 的往返开销。它对高性能网关、IPsec 卸载、AI 训练集群的东西向流量都有想象空间，而「消费级显卡即可达到 7000 万包/秒」意味着门槛远低于专用 DPU。
从只支持 AMD 独显扩展到 Intel Arc 与核显，说明项目正从原型走向通用化，值得跟踪它是否会以及如何被上游接纳——这类「把 GPU 当协处理器做数据面」的尝试往往先在实验项目里跑通，再逐步反哺内核。

KDE Plasma 6.8 下周发布：最后一刻修好 NVIDIA 专有驱动下的平铺卡顿
显示 display 图形 GPU
Plasma 6.8 定于 10 月 14 日正式发布，恰逢 KDE 项目成立 30 周年。
本周收尾修复中最值得关注的一条针对 NVIDIA 专有驱动：此前在特定 NVIDIA GPU 上平铺窗口会出现卡顿与掉帧，根因是每次打开 Qt Quick 特效都会重新创建 OpenGL 上下文，从而短暂阻塞主线程。修复方式是让 Qt 使用单一持久的 OpenGL 上下文。该问题 6 月上报（Bugzilla #522424），影响所有近期 Plasma 版本，并与 2024 年初的另一份报告（#479250）相关。
其余收尾项：KRunner 方向键键盘导航改进；Discover 对 Flatpak 应用的自动更新现在总能正确工作；修复 Slow Keys 辅助功能的按键重复问题。
Frameworks 6.32 还修了「输入时工具提示消失导致使用模糊效果的 Qt 程序崩溃」。Plasma 6.9 方面，KWin Overview 的虚拟桌面缩略图更协调美观，并支持控制登录后接入的键盘背光亮度。
关注理由：NVIDIA 专有驱动在 Wayland 合成器下的卡顿长期是 Linux 桌面的痛点，而这次是合成器侧用「持久 OpenGL 上下文」绕开驱动缺陷——属于务实且低风险的修法：不依赖 NVIDIA 改驱动，而是避免每次创建上下文带来的主线程阻塞。
考虑到 6.8 已是稳定前夜、并会随各滚动发行版进入用户机器，这类「最后一刻的多 GPU / 渲染修复」对日常体验的影响最直接——尤其对手上就是 NVIDIA 显卡、又用 Wayland 的开发者。

Linux 7.4 将带来大批笔记本与游戏掌机支持改进
计算 compute
x86 平台驱动的 for-next 分支已积累大量设备适配，将在 Linux 7.4 合并窗口中进入主线，覆盖笔记本与游戏掌机的多种外设与电源行为：
· ASUS：ASUS-NB-WMI 为 ROG Flow X13（GV302X*, 2023）加平板模式 quirk；Armoury 驱动为 ProArt（如 H7606 系列）等新机型增加独显开关的回退路径
· MSI：MSI EC 驱动为新固件的 Katana 15 B13VFK 与 GL65 Leopard 9SCXK 增加电池充电阈值控制
· HP：HP WMI 驱动为 OMEN 17-ck1xxx（板号 8A17）加温度档位支持，并新增 Victus 15-fb3xxx（8DD0）支持
· TUXEDO：Uniwill 驱动启用键盘背光与灯条控制
· Acer：Acer WMI 为 Nitro ANV15-51 加温度档位、硬件监控与风扇控制
· 掌机：OXPEC 驱动为 Intel 版 OneXPlayer 3 加电池旁路、容量限制、风扇曲线/转速、turbo 键覆盖等；AYANEO EC 驱动为 AYANEO 2S 加电池充电控制
时间线：7.4 合并窗口本月晚些时候开启，稳定版预计 2026 年底。
关注理由：这类「设备 quirk + 电源行为」补丁不像驱动重写那样引人注目，却直接决定一台笔记本在 Linux 上「能不能顺手用」——翻转屏能否正确进入平板模式、风扇曲线是否可调、掌机能否限制充电以保护电池、键盘背光开机后接入还能不能控制。
从中也能看出厂商态度：华硕、惠普、微星、宏碁，以及 OneXPlayer、AYANEO 这些掌机品牌，都在持续往上游送补丁。Linux 笔记本与掌机生态的适配速度明显加快，这对做 Linux 桌面/外设方向的人是一条值得留意的趋势线。

Meta 的可编程调试器 drgn 发布 0.3：加固不可信调试信息，支持 Linux 7.2/7.3
内核 kernel 计算 compute
Meta 开源的可编程调试器 drgn 发布 0.3，仍由内核开发者 Omar Sandoval 主导。其定位是「让脚本编写尽可能自然，使调试像写代码一样」。
本次重点：
· 加固代码库以应对不可信的调试信息与 core dump；
· 优化 QEMU 客户机调试——尽可能直接从 QEMU 进程读取内存，而非走慢路径；
· 新增若干便利函数（例如轻松读取系统 IRQ 数量）、新的 crash BPF 命令选项、crash net 命令的部分实现；
· 支持 Linux 7.2 / 7.3 的新内核特性；
· 正确识别 LoongArch64 架构，另含数十项修复与文档改进。
关注理由：内核崩溃现场调试长期依赖 crash 等老工具，脚本化能力弱、对非 x86 架构支持参差不齐。drgn 把「脚本化调试」做成主线能力，并持续跟进最新内核数据结构与 LoongArch64，对做驱动开发、稳定性排查与生产环境 core dump 分析的工程师是实打实的效率工具。
而「加固不可信调试信息」这一项尤其值得注意——它说明 drgn 已开始被用于更具对抗性的场景：当崩场来自外部、core dump 可能被构造时，调试器本身也成了攻击面。这在内核与安全团队协作中是个现实需求。

Linux 7.3-rc7 网络子系统：转移 50+ 修复到 7.4，仍被 AI 引发的补丁洪流冲击
内核 kernel
在 Linux 7.3-rc7 发布前，本周网络修复批次已完成合并。由于 7.3 周期接近尾声而补丁活动仍在高位，不紧急的修复被转入 net-next 供 7.4 使用——本次明确转移了 50 多个补丁，并要求各子树大幅裁剪。网络维护者 Jakub Kicinski 在拉取请求中直言：
「我很确定你不会对这个 PR 的体量感到满意，但这已经是我们砍掉 50 个修复、并要求子树显著裁剪之后的结果了。情况就是这样。」
本批仍含若干以太网驱动回归修复、联发科 MT76 Wi-Fi 驱动修复，以及不少「LLM 味」的修复。网络维护者此前已多次表示被 AI 活动「彻底淹没」，并遭遇 AI slop 补丁的困扰。
关注理由：这是「AI 新常态」在网络子系统最直观的一张切片：维护者不得不用「把补丁推迟到下一个内核」来换取评审带宽。对下游而言，这意味着大量非紧急修复的落地时点被整体后移，发行版回移的清单也随之变长；对团队而言，则提醒我们：把 AI 生成/发现的问题纳入内核或大型项目工作流时，必须同步规划评审容量，否则新增的「发现问题」能力会被流程瓶颈吃掉，甚至因低质补丁而反向拖慢主线。
这与此前内核「AI 金丝雀」「agents/ 资源目录」等动作是同一趋势的不同侧面。
